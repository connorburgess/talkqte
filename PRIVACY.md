# Privacy design

TalkQTE is an early desktop prototype with an optional microphone activity check. TalkQTE does not transcribe on this Mac or offer a local Whisper option. With your own transcription API key (Deepgram or ElevenLabs) and an API key for your chosen cue provider (Anthropic, OpenAI, or Gemini) stored, any build, ordinary and release builds included, immediately streams a live session's audio to the selected transcription provider and sends transcript lines to the selected provider's API for cue decisions when you press **Start live session** (or when opt-in call auto-start begins a session), as disclosed beside **Start live session** and in Settings; development lab runs still require approving the session's in-app processing review first. Without both required keys an ordinary build has no live transcription and says which key to add. Development cue backends and token files are described below. It is not a released meeting recorder. Current behavior and future requirements are separated below.

## Current prototype

- The app has no demo and plays no bundled dialogue; cues come only from a live session's transcript. On macOS 14.2 and later, any build, release builds included, captures system output audio (all other apps, excluding TalkQTE itself) alongside your microphone when you start a live session, using Core Audio Process Taps (`NSAudioCaptureUsageDescription`, macOS "System Audio Recording Only" permission) with **no Screen Recording permission** and **no audio written to disk**. On macOS earlier than 14.2, if you decline System Audio Recording Only permission, or on Windows and Linux test builds, live sessions fall back calmly to your microphone only. There is no speech model, TalkQTE account system, or telemetry integration, and no cloud cue model except the API provider you choose (Anthropic, OpenAI, or Gemini) with your own key and the development connections described below. Audio and transcript lines leave this Mac only to your chosen transcription provider (Deepgram or ElevenLabs) and your chosen cue provider, with your keys or a developer's, once you start a live session (or, in lab runs, approve the session's review). TalkQTE does not transcribe on this Mac and no longer downloads a speech model. A model that a build before 16 November 2026 downloaded stays in the app's data folder (`~/Library/Application Support/com.talkqte.desktop/models/`); the app no longer reads or deletes it, and you can delete that folder yourself.
- The macOS app, and the unsigned Windows and Linux test builds, can separately monitor activity from the default microphone after an explicit start action (and, on macOS, operating-system permission; Windows and Linux ask none, though Windows' microphone privacy switch can block it). It processes samples only to produce a coarse quiet/active indicator. Samples are not retained, recorded, logged, uploaded, or sent to the interface. It detects signal level, not speech, meeting participation, or the other side of a call.
- Monitoring starts off. Stop releases the input device on a worker, with a stopping state until release finishes; restarting is blocked during cleanup. A pending permission result cannot restart a cancelled session. Monitoring does not automatically restart or switch devices after an error. Hiding the companion does not stop microphone monitoring; only a live session's own microphone use ends with the session. Use Stop microphone or quit the app.
- **Voice dictation in Notes and Focus.** Clicking the microphone dictation icon button in **Notes** or **Focus** captures microphone audio in memory only (zero audio is written to disk) and streams 16 kHz mono PCM to your chosen transcription provider—**Deepgram** (`mip_opt_out=true`, default) or **ElevenLabs** (`scribe_v2_realtime`)—with your stored API key from the Keychain (or a Deepgram development token file when selected) in the transcription language chosen in Settings while active, appending finalized text back to that field. Nothing is captured or sent until you press the dictation button; it is disabled while a live session or the microphone check is active, or when no key is stored for the selected provider, stops automatically after a 2-minute limit, and pressing **Stop dictating** (or switching away from the field or quitting) ends capture, flushes queued audio on a normal Stop, and closes the stream. The selected transcription provider handles the sent audio under your account terms with that provider, and TalkQTE cannot recall audio once sent.
- A live session needs a cue connection (a key for your chosen cue provider — Anthropic, OpenAI, or Gemini — or a development `claude-cli` or lab connection) and a transcription credential (your key for your chosen transcription provider, Deepgram or ElevenLabs, or a development Deepgram token file), described next; without them a build has no live transcription and says which key is missing. It starts only when you choose **Start live session** (or when opt-in auto-start detects a call, if you enabled it in Settings): with the microphone (once the operating system grants microphone access), with one application you choose, or with both, as described below. Microphone samples pass through a bounded in-memory buffer and are streamed immediately to the chosen transcription provider while cue processing is active (in lab runs, samples are discarded until you approve cue processing). TalkQTE does not write them to disk or log them. The recognized text feeds cue evaluation. While the session runs, it stays in memory (the `timing-log` development build below also writes it to a file); once a non-empty live session stops, TalkQTE saves it locally to your kept meetings by default (below; changeable to ask each time or off in **Settings → Kept meetings**), and it is exported only if you choose: export is refused while a live session runs, and after it ends the export holds your notes only unless you tick **Also keep this meeting** in the export review for that session, which adds the transcript and the cues shown. Stop, in either window, releases the microphone, sends the last captured audio, waits up to 10 seconds for the last results, and ends the session; **Turn off processing** stops sending audio and transcript lines immediately while keeping capture running until you press Stop or re-enable processing; the session also ends if microphone access is refused, the device fails, or transcription stops. Quitting discards queued audio. Both windows see the live cue and its source line; the companion can pause cues, turn off processing, or stop the session, and starts one only when you click **Start** on the call offer or opt in to auto-start. Without the `native-audio-spike` development feature, other apps' audio is not captured.
- Live sessions are transcribed through your chosen provider—**Deepgram** (default) or **ElevenLabs** (Scribe v2 Realtime)—with your own API key from the Keychain ([provider keys](docs/provider-keys.md)), at most 120 minutes of audio per session (no per-launch or per-day cap), billed to your account with that provider. Instead, a debug build with the `cloud-transcription` feature, which `lab-evaluator` switches on and which no default or release build includes, can be pointed before launch at `TALKQTE_DEV_STT_BACKEND=deepgram`, the path of an owner-only file holding a short-lived Deepgram token, and a cap of 1 to 60 minutes of audio for the whole launch, across sessions and sources; that development selection wins over a stored key and always uses Deepgram. **When:** in ordinary builds, pressing **Start live session** (or opt-in call auto-start) immediately begins sending audio from the selected source(s) to the selected provider (Deepgram or ElevenLabs) until you press **Stop** or **Turn off processing**; in lab runs, nothing is sent until you approve cue processing for the session in the app, whose review names the selected provider (Deepgram or ElevenLabs) as the audio destination, what is sent and the cap (until then captured audio is discarded and never sent). **What:** the audio of the capture sources the session was started with, and only those, which the disclosure beside **Start live session** and **Cue processing** name: the microphone, one selected application's audio (all of its windows may be included), or both as two streams that share the session's one minute cap; as 16 kHz mono PCM, with the key or token in a request header (`Authorization: Token …` for Deepgram, `xi-api-key` for ElevenLabs). An application can join only a session started with it. Notes, names, focus lines and the transcript are not sent to the transcription provider. **Request settings:** Deepgram requests carry `mip_opt_out=true`, asking Deepgram to opt out of its Model Improvement Program, and request Nova-3 transcription in the language chosen in Settings before the session (English by default, or Multilingual, which Deepgram bills at a higher rate), with punctuation and speaker labels; the speaker labels are never shown or sent to a cue model, and only the `timing-log` build records them. ElevenLabs requests connect to `wss://api.elevenlabs.io/v1/speech-to-text/realtime` for `scribe_v2_realtime` with `audio_format=pcm_16000`, `commit_strategy=vad`, `include_timestamps=true`, and `language_code=en` for English (omitting `language_code` for automatic language detection when Multilingual is chosen); TalkQTE sends no zero-retention or opt-out flag to ElevenLabs, and retention/opt-out follows ElevenLabs' own terms. In a session with both sources, TalkQTE labels each line "You" (microphone) or "Them" (application) by where it was heard, not who spoke; these labels stay on the Mac (the cue model still receives a fixed "Speaker"), and a microphone line that closely copies one application line (a likely echo through the speakers) is never sent to a cue model; it stays in the transcript, marked, and in a kept meeting marked the same way, unless you remove it. **Ending:** turning cue processing off, the end of a lab cue run (including Pause in the lab), the launch's cap, a refused key or token (a refused key is then shown as rejected), an exhausted account or rate limiting stops sending and ends the session with a plain reason, with no fallback to another transcription service and no retry. A lost or stalled connection, or a provider server error, is replaced by a new connection under the same grant and cap at most twice per source in a session, and the notebook says how much speech was missed; after that the session ends the same way. Stop sends a microphone session's already-captured audio and waits up to 10 seconds for the last results; an application-audio session, End and quit close the stream at once. **What is kept:** TalkQTE writes no audio, key or token to disk. The selected transcription provider handles the audio under the key holder's terms with that provider, and TalkQTE cannot recall audio once sent ([details](docs/cloud-transcription.md)).
- **System audio on macOS 14.2+.** When you press **Start live session** (or click **Start** in the floating dock, or opt in to call auto-start), TalkQTE opens your microphone (`You`) and creates a private, unmuted Core Audio global system audio tap (`AudioHardwareCreateProcessTap` with `CATapDescription` excluding TalkQTE's own process) (`Them`). macOS asks only for **System Audio Recording Only** (`NSAudioCaptureUsageDescription`) on first use—no Screen Recording permission is requested or needed, and no app picker is required. System audio is downmixed in a lock-free in-memory ring buffer (`rtrb`), resampled to 16 kHz mono PCM, and streamed to your chosen transcription provider while cue processing is active (never written to disk). If you decline system audio permission or run macOS earlier than 14.2, TalkQTE falls back cleanly to microphone-only capture with a notice. Development lab builds with the `native-audio-spike` feature retain isolated single-app test hooks (`TALKQTE_DEV_APPLICATION_SOURCE`, `TALKQTE_DEV_APPLICATION_WITH_MICROPHONE=1`, `TALKQTE_DEV_STOP_AFTER_S`) for unattended fictional lab runs ([details](docs/native-application-audio-host.md)).
- **When a call starts (offer on by default on macOS; auto-start off by default).** Under **Settings → When a call starts**, **Offer in the dock when a call seems to start** is **on by default** on macOS (disabled in lab runs) and can be turned off at any time in Settings, from the menu bar, or by clicking **Off** on the offer itself; **Start automatically when a call begins** remains **off by default** (never enabled in lab runs), so nothing is captured or sent until you click **Start** or explicitly opt in to auto-start. While either toggle is on, TalkQTE reads only local metadata while it is open (every 500 ms): whether the microphone or camera is active and the app's name and bundle identifier (Core Audio process and device metadata on macOS 14.2+, CoreMediaIO device metadata, and the frontmost app's name and bundle identifier — neither the microphone nor the camera is opened, and TalkQTE ignores its own process and bundle identifiers). It never reads audio, video frames, window titles or screen content, and all of this stays on the Mac. With **Offer in the dock** on, after 1.5 seconds when a known meeting app or browser is identified (or 3 seconds for generic microphone-only use) the dock shows a compact 1-click **Start** offer (**Start**, **Not now**, **Not for <app>**, and **Off**) that immediately starts listening and processing if clicked, without taking focus. With **Start automatically when a call begins** on, when a known meeting app or browser activates your mic or camera preview (and your keys are configured and no session is running), TalkQTE automatically starts the live session (with microphone and macOS system audio) and displays **`Listening · Stop`** in the dock so you can see it is active and stop in one click. Nothing is read while both toggles are off. Both settings, **Off** (which turns the dock offer off) and **Not for <app>** are kept in the settings file below; **Not for <app>** is kept as the app's bundle identifier (for example `us.zoom.xos`), and only for the known meeting apps and browsers it recognises ([details](docs/call-prompt.md)).
- **Calendar & call prompts (macOS, off by default).** If you turn on **Settings → Calendar & call prompts → Use macOS Calendar for upcoming meetings**, TalkQTE asks macOS for Calendar access (EventKit) and checks Apple Calendar every 15 seconds while no live session is open, reading only events in a tight window (starting within the next 5 minutes or currently in progress within the first 10 minutes). For each event in that window, it extracts only the event identifier and start time (for once-per-event deduplication), a sanitized title, start/end timestamps, and a boolean indicating whether its URL, location, or notes contain a known meeting link (`meet.google.com`, `zoom.us`, `teams.microsoft.com`, `teams.live.com`, `webex.com`, `whereby.com`, `around.co`, `tuple.app`, `chime.aws`, `meet.jit.si`, `discord.gg`, or `huddle`). Attendee lists and organizers are never accessed. URL, location, and notes text are read transiently to detect a meeting link, then discarded; they are never kept or uploaded. Events outside the supported start window are filtered before their title or link fields are read. The floating companion receives only the prompt ID, sanitized title, and rounded minutes until start (never raw calendar fields or links). Clicking **Prepare session** opens the notebook with that title pre-filled as the default meeting title for your session and local kept-meeting record; the meeting title is never sent to Deepgram, ElevenLabs, cue providers, or the companion end-of-call card. Nothing is read or requested while the setting is off, on Windows/Linux, or in lab runs.
- A development build with the `claude-cli` feature, which no default, release or `native-audio-spike` build includes, can send conversation lines off this Mac to Anthropic for cue decisions. That is hosted processing, through the Claude Code CLI installed on this Mac and your own signed-in Claude subscription. It exists for the owner's own development use and is not a product feature.
  - **When.** Nothing is sent until you review and turn on **Cue processing** for the session, except in a debug build with both `claude-cli` and `native-audio-spike` when the developer explicitly sets `TALKQTE_DEV_MODEL_CONNECTION=on` at launch. That setting approves recent and new conversation only, never prior notes, for each live session in that launch; the panel discloses it. These builds cap requests per session at 100 by default, adjustable down with `TALKQTE_DEV_MODEL_CALLS`; Off/On and Pause/Resume do not reset the count. Invalid launch settings leave cues off. See [launch consent](docs/real-app-lab.md#model-connection-without-clicks). After that, a request goes after each new transcript line, at most once every two seconds and one at a time. Sending ends when you turn it off, stop the session or quit, or when a failure stops it; quitting, Ctrl-C or a terminal hang-up ends any request on its way and any helper it started. The notebook says while lines are being sent, and the companion shows a cloud while the connection is on, with an arrow while a request is on its way.
  - **What.** Each request holds up to six recent transcript lines and any lines the cue on screen cites, the cue on screen, up to four earlier cues with how each ended, and your session name if you set one. Because a request follows each new line, over a session nearly every transcript line is sent, a few at a time.
  - **Never sent.** Audio, the full transcript in one request, notes you type, unapproved imported or Granola notes, focus lines and device names. Supported own-key selected-note sharing requires a separate exact-snapshot review; imports alone do not authorize it.
  - **Refusals.** The app refuses to start the CLI when the environment carries an API key, provider switch, gateway or proxy setting, so nothing is billed through an API.
  - **Failures.** Any failure stops sending for the session and shows why. A single slow reply is skipped, and two in a row stop sending.
  - **What Anthropic keeps.** What is sent is handled under your Claude account's terms and settings. The CLI runs with session persistence off, which does not remove the provider's own retention, and lines already sent cannot be recalled ([design](docs/cue-model.md)).
- A development build with the `timing-log` feature, which no default, release or `native-audio-spike` build includes, can write a timing log for lab runs with fictional audio. It writes only when the developer sets the `TALKQTE_TIMING_LOG` environment variable to a file outside the repository, and then records every session until the app quits, microphone sessions included. Each line holds its time and one of: a session starting or ending, with the build's commit and features; a chunk of audio handed to transcription, with its timing and whether it was silent, never the audio itself; a recognized line with its speaker label and full text; or a cue decided, sent to the companion or cleared, by its id and kind. With a model connection it also records the connection turning on or off, with its backend, model, effort and whether approval came from review or the launch setting; a session cap stop as `evaluation_stopped` with failure `call_limit`; each request, by number, with the last line covered and how many lines were sent; and each result, with its outcome, latency and a fixed failure code. The prompt and the raw reply are never written. A cue the model proposed is written by its id, not its words, and a request ended by Stop, Pause or turning the connection off is written as cancelled. A cue's question and source line are written only for a phrase cue raised by a transcript line. A cue that quotes an imported or Granola note, lists the focus lines or concerns them is written without its question, note or focus text. The file is created readable by its owner only, is only appended to, and nothing is sent anywhere ([details](docs/real-app-lab.md#timing-log)).
- **Copy diagnostics** (Settings → Diagnostics) shows, for a problem report, the app version, your settings, whether each key is set, the session's state and the fixed codes of what last went wrong, then copies that text to the clipboard when you choose **Copy diagnostics**. Every field is taken by name from a fixed list and free text is replaced, so it holds no transcript, notes, cues, focus lines, name, application or device names, file paths or keys; a browser test fills each of those with fictional content and checks none appears ([`tests/diagnostics.spec.ts`](tests/diagnostics.spec.ts)). Nothing is sent or saved; what you paste is up to you.
- A headless test runs a cue session with your key against a scripted provider (a cue, then an outage), with notes, focus lines and a name set, builds a kept meeting, and asks for meeting notes that are refused, in a process whose home, data and temporary folders point at an empty folder, with the timing log asked for. It checks that the folder stays empty (in a `timing-log` development build, that the timing log is the only file) and that none of that content or the key is printed (`a_cue_session_with_failures_and_notes_writes_nothing_and_prints_nothing`). Crash output from a real crash, and the storage and logs of a built app after a real session, are not yet checked.
- TalkQTE does not tell other people that their voices are being captured and does not collect anyone's consent. A live session's microphone can pick up anyone speaking near it. When you choose an application for a session, TalkQTE captures that application's audio, from all of its windows (for a call app, every participant you hear in it; for a browser, possibly other tabs too), so other participants are heard that way. When cue processing is on, the speech of anyone the microphone or the chosen application picks up is sent to the selected transcription provider (Deepgram or ElevenLabs), a third-party service; TalkQTE does not prompt you to tell them. If anyone else may be heard, telling them and obtaining any consent your local law requires is your responsibility.
- What TalkQTE never captures: video, screenshots, or any picture of the screen (no Screen Recording permission is requested), its own audio output (TalkQTE's own process is excluded from the Core Audio process tap), or any audio outside an explicit live session / microphone check / dictation action. It installs no virtual audio driver, and writes no audio to disk.
- The optional name in Settings is kept in the settings file below so it is there at the next launch; focus lines are kept in process memory for the session and cleared when the app quits. They are excluded from Markdown export. The name may be sent with conversation only after the cue-processing approval described above or below; focus lines are not sent to the cue provider. They are not sent to the companion as settings fields (it learns that a question is about the focus, and a Still open list names the focus lines not yet discussed).
- Prior notes you import from a file you choose are read once into memory while you choose, and released when you import, cancel, or close the chooser; only the notes you tick are kept, for this session, listed in the notebook's **Prior context** section, which is closed until you open it, and labeled as not from the conversation. Remove deletes the imported copy and clears any current reminder quoting it, including a reminder held open for reading. A note may be shown once as a reminder in the companion when the conversation uses words from its title, labeled as coming from your notes; that happens on this device only. Imported notes are excluded from Markdown export and are not persisted by TalkQTE. They stay on this device unless you explicitly approve the selected-context development API export described next; nothing reads a file you did not pick.
- The development API lab can explicitly select `selected-prior-v2` context. Only after the session review approves exact stored note snapshots can it send their excerpts, titles, source labels, dates and opaque snapshot versions, together with approved conversation, the optional session name and current/earlier cues, to the Anthropic API. Importing or selecting a note is not processing permission. Saved snapshots are not verified current. Approving zero notes sends none, using the same selected-context prompt and route. Default API, subscription and standalone CLI paths still exclude prior notes; this mode sends no audio, manual notes or focus lines to the cue provider. The review names API billing, the per-run cap, request limits, retention and any separate transcription destination. Changing or removing an approved note invalidates its grant and pending/held cue evidence; Off and Stop prevent future requests and reject late replies but cannot recall content already sent. This is a separately enabled fictional lab path, not real-account or live-usefulness acceptance ([scope and remaining gates](docs/selected-context-lab-opt-in.md)).
- Your own provider keys: **Settings → Your API keys** stores API keys for **Deepgram**, **ElevenLabs**, **Anthropic**, **OpenAI**, and **Gemini** (`deepgram`, `elevenlabs`, `anthropic`, `openai`, `gemini`), which you create in your own accounts. They are kept only in your system's secret store under the service `app.talkqte.provider-key`: the login Keychain on macOS; in the unsigned Windows and Linux test builds, Windows Credential Manager (generic credentials for this user on this computer) or the desktop keyring through the Secret Service (GNOME Keyring on Ubuntu). Where Linux has no keyring service, keys cannot be saved and are not kept anywhere else. They are never written to a file, never logged and never shown again; the notebook only learns whether each key is set, has been checked, or was rejected. Storing a key sends nothing. **Test** sends one read-only request only to that key's provider (Deepgram's project list with `Authorization: Token …`, ElevenLabs' user record with `xi-api-key`, Anthropic's model list with `x-api-key`, OpenAI's model list with `Authorization: Bearer …`, or Gemini's model list with `x-goog-api-key` in the request header and never in the query string), which neither transcribes nor generates anything. **Remove** deletes the key from that store. Under **Settings → Transcription provider**, you choose **Deepgram** (default) or **ElevenLabs**; that chosen transcription provider's key is used for transcription and the key for your chosen **Cue & notes provider** for cue decisions and meeting notes, as described below. See [provider keys](docs/provider-keys.md).
- Cue decisions with your own key: when you start a live session (or turn processing back on via **Cue processing → Review processing**), which names your selected transcription provider (Deepgram or ElevenLabs) and your chosen cue provider (the Anthropic Messages API, OpenAI Responses API with `store: false`, or Gemini REST API with `x-goog-api-key` header) beforehand beside **Start live session**, the app sends up to six recent transcript lines (labelled only `Speaker`) and any lines the cue on screen cites, the cue on screen, up to four earlier cues with how each ended, and your session name if you set one. It sends after new lines, at most once every two seconds, at most 400 requests and (for built-in curated models) an estimated $0.50 per session, with the key only in a request header. Custom model IDs outside the built-in price table still enforce the 400-request session cap and report estimated spend as unavailable rather than guessing dollar cost. The caps are per session; there is no per-launch or per-day cap. Pause cues stops these requests but not the audio to the transcription provider, which is still sent and billed until you turn processing off or stop the session. It never sends audio, the full transcript, your notes, focus lines, or unapproved imported notes. During active capture, **Cue processing → Review prior-note sharing** can separately approve exact selected copies, with their source metadata and opaque revisions, without stopping capture. Undated files stay unknown; source changes/withdrawal cancel pending effects, and removing the last selected copy returns to new speech only without resetting session budgets. That provider bills your account and handles what is sent under your API account's terms; lines already sent cannot be recalled. A refused key, a rate limit, a failure or a cap stops cues for the session with a plain reason; nothing falls back to another service and nothing is retried. The request count and spend estimate stay in memory ([details](docs/own-key-cues.md)).
- Meeting notes with your own key: after a live session has ended, **Write meeting notes…** in the notebook can ask your chosen cue & notes provider (Anthropic, OpenAI, or Gemini), once for that meeting, to write a summary, decisions, action items and open questions from its transcript. This is separate from the session's processing review, which ended with the session, and nothing is sent until you confirm a second time. Before you confirm, the notebook shows what will be sent (the session's whole transcript, with each line's time from the start and remote speaker labels, including custom names when set, and your own notes only if you tick **Also send my notes**, off each time), to whom (that provider's API, with your key, billed to your account), the chosen curated or custom model, its size, and — for built-in models — an estimated cost with its worst case (for custom model IDs outside the built-in price table, estimated cost is shown as unavailable). The session name, focus lines, imported or Granola notes, the cues shown and audio are never sent for notes. One request per meeting, with no retry and no other model or service; a transcript beyond 4,000 lines or 240,000 bytes is refused before sending, and so is any built-in model request whose worst-case estimate (one token per byte) passes $1.00. The request sent is exactly the one the confirmation described; if the transcript, your notes or the notes setting change first, it is refused and shown again. **Stop waiting** before the request leaves sends nothing. The reply is checked: every item must cite lines that were sent, and an owner is shown only when named in the cited text or a custom speaker label, and a date only when stated in the cited text. Notes that fail a check are shown as failed, not repaired. Those checks do not make the notes true: a model can still write an item that is invented or misleading, including from words someone said in the meeting to steer it, so check each item against the lines it cites. Links, images and HTML in the model's text are removed or escaped before you see it, so the export loads nothing from it. The notes stay in memory: they reach a file only if you keep them and then export, and the next session clears them. That provider handles what is sent under your API account's terms, and it cannot be recalled ([details](docs/meeting-notes.md)).
- Connecting Granola is your choice, in the desktop app only. The sign-in happens in your browser with Granola; the app receives an access token through a one-time return address on this Mac and keeps it in memory, never on disk. Disconnect invalidates all copies of the connection without waiting for the network and discards delayed results, even after a new connection opens. Idle credentials are dropped immediately; an already-running request may finish before its credentials and response are dropped. Disconnect also cancels pending sign-in. Imported copies remain until you remove them. With that token the app asks Granola's documented MCP server for your note list, for the notes you tick, and, if you press **Suggest from Granola**, one fixed question to its assistant; nothing else: no transcripts, no writing back, no other account data. Granola sees the sign-in and those requests, with a `TalkQTE` user agent. The notebook shows whether a connection is open, which tools the server offers, and, for notes you kept, whether an update check is available and the result of the last one; it never shows whose account it is. An update check runs only when you press it and asks again only for notes you already kept; it is not offered for a Granola connection today, so no such request is sent. The suggestion step sends only that fixed question; Granola's model answers from notes it already holds, the answer is shown for you to tick, and only the lines you add become focus lines on this device. No transcript, note, or focus line of yours is sent by that step.
- The optional `TALKQTE_GRANOLA_TRACE` developer diagnostic prints bounded structures to stderr: known field names, string lengths, collection sizes, and a tag outline. Arbitrary JSON keys, scalar values, tool descriptions, and schema defaults are masked; raw tool schemas are not logged. Your terminal may retain this output. The diagnostic is off unless explicitly enabled; it is not an automatic upload or a guarantee about provider or operating-system logs.
- No cue is written to your notes. A quoted line, like any other cue, is shown and then let go, whether you hold it, dismiss it or leave it. The **Keep this line** button, which appended a quoted sentence to your notes, was removed on 14 November 2026.
- The transcript and your notes live in process memory. Dismissed or expired questions are let go; nothing keeps them as notes or action items. Starting or stopping a live session keeps notes. Quitting the app clears everything. There is no database, recovery, retention scheduler, or encrypted notebook.
- **Settings file.** Your choices in Settings are kept in one small file, `~/Library/Application Support/com.talkqte.desktop/settings.json`, readable by your macOS account only (mode 600) and replaced whole on each change. It holds preferences only: the transcription provider, the transcription language, your chosen cue provider (`cueProvider`) and optional cue/notes model IDs (`cueModelOverride`, `notesModel`, `notesModelOverride`), question text size, question timing, the companion's position preset and whether it is shown, notebook panel sizes, your name, the call-starting setting, the opt-in Calendar prompt toggle (`calendarPrompts`), the bundle identifiers of apps it should not ask about, whether ended live meetings are saved automatically, asked about, or left unsaved, whether relevant recent kept meetings are auto-selected as prior context (`autoPriorContext`), whether to keep running in the menu bar, and whether to check for app updates at launch (`checkForUpdatesAtLaunch`, on by default). It never holds a provider key (those stay in the Keychain), a transcript, notes, cues, focus lines, the applications you chose for a session, or anything else from a meeting. A place you drag the companion to is not kept. It is read once at launch; anything unreadable takes its default. **Settings → Saved settings → Reset settings** deletes the file. A development lab run neither reads nor writes it.
- **In-app updates.** Signed builds check `https://github.com/connorburgess/talkqte/releases/latest/download/latest.json` over HTTPS (at launch when **Check for updates on launch** is enabled, or when you press **Check for updates** in **Settings → Updates**), sending no meeting data, keys, notes, or user identifiers—only standard updater HTTP request headers. Builds without a configured minisign public key report `"Updates are not configured in this build"` and make no network requests. Downloaded archives must pass minisign signature verification against the compiled-in public key before replacing the app, and update checks, offers, installs, and restarts are deferred or refused whenever a live session, microphone check, application audio capture, or voice dictation is active, and in lab runs. Updater commands are restricted to the main notebook window.
- **Menu bar and login (both off by default).** TalkQTE has a menu bar item that shows whether a session is running. It reads nothing new: the item shows the session's state and the call-starting switch, and its Start session… opens the notebook's usual start and approval. With **Keep running in the menu bar** on, closing the notebook leaves TalkQTE running, so the call-starting prompt, if on, keeps watching; quit from the menu bar to stop it. **Open at login** asks macOS to open TalkQTE at login through `SMAppService`. macOS keeps that setting, not TalkQTE's settings file, and you can remove it in System Settings → General → Login Items. A lab run never registers it.
- **Kept meetings (auto-save by default; ask or off in Settings).** By default (**Settings → Kept meetings → After a live session ends**: **Auto-save to Meetings**), when a non-empty live session stops (with transcript lines or manual notes), TalkQTE saves it right away under a date-and-time title (never the captured application's name on auto-save) and shows a **Meeting saved** card in the floating dock (**Write notes**, **Open**, **Delete**, and **Dismiss**). You can switch **After a live session ends** to **Ask each time** (floating dock shows **Meeting ended** with **Keep meeting**, **Write notes**, and **Dismiss**; notebook shows **Keep this meeting?** where you can also opt into keeping the application's name) or **Don't keep automatically or ask**; both choices save to `settings.json`. Under **Ask each time** or **Don't keep automatically or ask**, nothing is stored unless you choose **Keep meeting** (and **Not this one**, dismissing, quitting, or starting another session stores nothing). Completely empty sessions and lab runs never auto-save and show no dock prompt. A kept meeting holds its title (yours, by default the date and time), date, length, which sources it used (microphone, application or both; the application's name only if you explicitly tick **Also keep the application's name**), the transcript with times from the start (source labels, remote diarization IDs and per-meeting custom speaker names, with likely echoes marked unless you removed them), your notes, the cues shown from the conversation (each with the transcript line it quoted) and meeting notes only if you kept them. It never holds audio, a provider key, your name setting, focus lines, imported notes, note reminders or the Still open list. After keeping (whether auto-saved or manually kept), notes or meeting notes you add to that session are written to the kept meeting only when you choose **Update kept meeting**. **Where:** files under `~/Library/Application Support/com.talkqte.desktop/meetings/` (an `index.json` list and one folder per meeting), in a folder only your account can open (mode 700, files 600), each written atomically. **They are stored unencrypted** on the Mac's disk under your account: anyone or any program running as your account can read them, and FileVault, if on, encrypts the disk as a whole. They are included in backups of your account, such as Time Machine. **Versions:** each file states its format; a history written by a newer TalkQTE is neither changed nor overwritten by an older one, only read-only until **Delete all meetings**. Files are size-bounded and checked on read; one that fails is not shown and is never rewritten. **Browsing and exporting:** **Meetings** in the notebook lists unfiled meetings newest first followed by optional collapsible folders (folder names and assignments stay locally in the meeting index), searches by title, folder, or text, opens them read-only, and lets you rename, move between folders, archive/unarchive (with a **Show archived** filter), delete, or export one as Markdown through the same preview-before-destination dialog. **Prior context:** by default (**Settings → Meetings → Auto-select relevant past meetings as prior context**, on by default and opt-out in Settings; never enabled, read, or written in lab runs), TalkQTE pre-selects up to 3 non-archived kept meetings that have kept meeting notes or your own notes (up to 2,000 characters per meeting, **notes only—never transcripts, cues, or application names**), ranked by keyword overlap with your Focus or session title and falling back to most recent, and you can also pick more with **Prior context → Choose kept meetings**. Auto-selected items are labelled `Auto` in **Prior context**, stay in memory for the session, remain excluded from Markdown exports, and are **never sent to a cue provider unless you turn processing off and explicitly tick them in that session's processing review**, with citations back to that meeting. Clicking **Remove** removes an item for the rest of that session (it is never re-added during that session), and clicking **Archive** (in **Prior context** or **Meetings**) permanently excludes that meeting from future auto-selection until you unarchive it. **Removing them:** **Delete** on the floating dock card removes the just-saved meeting right away; deleting a meeting in **Meetings** removes its folder; Settings → **Delete all meetings** removes the whole `meetings` folder, including any file that could not be read; quitting TalkQTE and deleting that folder does the same. A copy already in a backup or an export is outside TalkQTE's control. **Lab runs:** a launch with lab settings (`TALKQTE_DEV_LAB_RUN_ID`, `TALKQTE_TIMING_LOG`, `TALKQTE_DEV_CUE_BACKEND`, `TALKQTE_DEV_LAB_DESCRIPTOR`, `TALKQTE_DEV_LAB_CONTEXT`, `TALKQTE_DEV_APPLICATION_SOURCE` or `TALKQTE_DEV_PLAYER_PID`; debug builds only) neither reads nor writes kept meetings ([details](docs/meeting-history.md)).
- Apart from the settings file and kept meetings, a Markdown export is the only implemented persistence. You review the generated text, then choose the file destination in a native save dialog. The saved file contains exactly that preview. By default it holds your notes only: no transcript, cue, name, focus line or imported note. For an ended session you may tick **Also keep this meeting** in the review, off for every new session, to add that session's transcript (times from the start and source/remote speaker labels, including custom names) and the cues it raised from the conversation, each with the transcript line it quoted. Reminders quoting an imported note and the Still open list of your focus lines are left out, so no imported-note content, focus line or session name setting is written; words people said aloud, names included, are in the transcript; the preview updates before you choose a destination, and nothing is written until you do. Meeting notes written with your key (above) are added after your notes only if you chose **Keep with this meeting**, as you edited them. Export itself makes no model call; there is no automatic saving and no background file. The destination may be a folder synchronized by other software; exported files are outside TalkQTE's control.
- The floating window receives only the current question, its source excerpt, end-of-call prompt counts (never transcript text, notes, titles, IDs, or application names), and the state needed to display it. It cannot write to or edit your notes, and it cannot export.
- Both windows receive microphone status, coarse activity and a bounded display name for the opened input, without samples, device identifiers or precise levels. The input name is read only after an explicit start and microphone permission, kept in memory for that stream, and displayed beside microphone status in the notebook/Settings. It is never written to notes, exports, logs or provider requests. It clears from status on release or error. Only the main window can start monitoring; the companion can stop it. The browser preview never requests microphone permission.
- The app has no automatic upload feature. The development server uses loopback connections, and installing dependencies requires network access. The browser preview downloads exports through the browser and is not a separate production service.

Do not use this prototype for real or sensitive meeting data. Closing the app loses unsaved notes, and there is no implemented storage protection beyond the operating system's process boundaries. The owner has reported a bounded activity-monitor acceptance check; device-specific disconnect/recovery details and the separate cloud-transcription path still need native verification. See the [acceptance record](docs/native-validation.md#owner-reported-microphone-acceptance--11-november-2026); synthetic tests do not prove those platform behaviors.

## Explicit transcript questions

Ask is a separate, explicit processing boundary: opening it sends nothing; **Send** authorizes the question and the provider/model/transcript range shown beside it. The excerpt is at most the latest 200 available current-session lines within a bounded input size. It excludes speaker labels, saved/imported notes, earlier discussion outside the range and previous Q&A. Keys remain in Rust and existing fixed provider HTTPS routes are used. Scope/provider changes require a fresh native ticket, without a repeated modal for growing speech. Stop, Off, Cancel and new sessions retire pending answers; remote content already sent cannot be recalled. The last ten successful Q&A entries stay only in current-session memory and never enter kept meetings or exports. Provider account retention terms apply; offline tests are not a traffic or retention audit. See [all controls and limits](docs/live-questions.md).

## Optional fictional development lab

The [Claude cue lab](docs/claude-cue-lab.md) is a separate, explicitly invoked development script. A selected bundled fictional scenario is sent to Claude through the user's subscription; this is hosted processing. It has no microphone, live transcript, arbitrary-file input, or connection to the desktop engine. Listing cases, dry runs and offline tests do not invoke a model. A [bounded batch](docs/cue-simulation.md) sends each selected fictional case the same way, one request at a time, only when explicitly run with a call cap. The timing simulation sends lines of a bundled fictional conversation the same way, under the same flags: up to 100 requests in one invocation, each with up to six recent lines, the lines the cue on screen cites, that cue's text, the fictional listener's name, and the text of up to four cues shown earlier in the same conversation; cue text may be text the model wrote in an earlier reply. The lab's recorder sends nothing anywhere: it plays a results file of a bundled fictional conversation in the browser preview on the same device, speaks the lines with the system's own voices, and writes its videos to a directory the user names outside the repository. A separate, optional voice step can instead send the lines of a bundled fictional conversation to OpenAI's text-to-speech service to make more natural synthetic voices; it runs only when explicitly started with a character cap and the user's own key, and sends nothing but those fictional lines, a preset voice name and speaking instructions. The lab's [meeting emulator](docs/meeting-emulator.md) plays only fictional conversations and sends nothing anywhere; its window-only recorder records just the emulator's window and the TalkQTE companion's window with the emulator's sound, never the whole screen, needs the Screen & System Audio Recording permission, and writes outside the repository. A second optional step can send descriptions of invented people, naming no one, to OpenAI's image service to make portraits for the mock call, under the same conditions.

The [dialogue lab](docs/cue-dialogue.md) generates fictional conversations in which a simulated listener responds to cues. Its dry run and offline runs, with deterministic fakes, send nothing anywhere. A model run, which has not yet been made and needs the owner's go-ahead, sends each request to Anthropic through the same subscription sign-in and isolation, under one call cap of at most 300 for the whole run:

- **the generator**: a domain, a number and the counts of moments to write;
- **the other participants**: one generated fictional meeting's title and setting, the invented people's roles, goals and private facts, the listener's name and role, the transcript so far, whose turn it is and how many turns are left;
- **the listener**: the meeting, its own invented goal and facts, the others' names and roles, the transcript as it heard it, whether it has the floor, and the text of a cue card when one is shown and of cards it read earlier, which may be text the cue model wrote;
- **the cue evaluator**: what the timing simulation sends;
- **the judge**: the meeting's title and setting, the people's names and roles, the brief's criteria, and one transcript.

All of that text is invented by a model or by hand; no real conversation, file or note is read. The run writes its briefs, results, reviews and an event log holding every request and reply to a directory the user names outside the repository, and omits raw CLI output, session IDs, account identity and credentials.

The runner disables tools, customizations, MCP connections, and session persistence, uses a temporary working directory, and prints a filtered report to stdout. A batch or simulation also writes a results file and an event log to a directory the user names outside the repository; they hold the exact input of every request and every model decision, and omit raw CLI output, session IDs, account identity and credentials. It does not store a meeting archive or extract credentials. These controls do not establish zero provider retention or prevent all CLI diagnostic/account state. Review the CLI and provider settings independently before any future work with real content. No such input path is implemented here.

## Requirements for meeting capture

- Capture begins only after an explicit action. Show whether the microphone, system audio, or both are active.
- Provide a visible pause/stop control and an accessible shortcut. Stopping capture releases the devices.
- Transcription (Deepgram or ElevenLabs) and cue decisions (the Anthropic, OpenAI, or Gemini API chosen in Settings) use named cloud providers only after the person turns them on for that session. They are off by default and can be turned off at any time. Every Deepgram transcription request asks Deepgram to opt out of model improvement; ElevenLabs retention and opt-out are governed by ElevenLabs' terms. Disclose which provider receives audio or text; provider handling and retention remain subject to that provider's terms. Nothing falls back silently to another provider. Audio and lines are sent only after the session's in-app processing review is approved. It has no local transcription option. A new processing choice needs its own review and acceptance.
- Without that consent a session has no transcription and no cues; there is no on-device transcription mode. No TalkQTE account or telemetry is needed.
- Keep credentials and personal data in application-managed storage outside the checkout. The frontend receives only the data it needs.
- Raw audio is held in a bounded memory buffer and not written to disk by default. Debugging must not silently create recordings or dump transcripts into logs.
- Sharing is explicit: show the destination and the exact content being exported. Integrations are off until enabled and scoped by the user.
- No private meeting data belongs in the public development repository, review services, demos, or CI artifacts.

Data kept on the device is not inaccessible to the device owner, an administrator, malware, or backups. Data sent to a provider is handled under that provider's terms, and TalkQTE cannot recall it. Do not describe local storage as encrypted until encryption is implemented and tested. Plan for protected storage and OS keychain-managed keys before recommending TalkQTE for sensitive meetings.

## Proposed retention defaults

These defaults remain open to product feedback:

| Data                                             | Proposed default                                                                                                                                      |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Raw audio                                        | Memory only in TalkQTE; sent to the selected transcription provider (Deepgram or ElevenLabs) while transcription is on, not kept by TalkQTE once sent |
| Full transcripts                                 | Delete after 30 days; offer session-only, 7 days, 30 days, and keep until deleted                                                                     |
| Explicitly saved notes, decisions, and questions | Keep until the user deletes them                                                                                                                      |
| Temporary analysis and search indexes            | Follow the retention of their source data                                                                                                             |
| External exports                                 | User-controlled copies; local deletion cannot revoke them                                                                                             |

This table covers only what TalkQTE keeps. What a provider keeps is set by its own terms: Deepgram's [terms of service](https://deepgram.com/terms), [privacy policy](https://deepgram.com/privacy) and [model improvement program](https://developers.deepgram.com/docs/the-deepgram-model-improvement-partnership-program), which every TalkQTE Deepgram request opts out of; ElevenLabs' [terms of service](https://elevenlabs.io/terms) and [privacy policy](https://elevenlabs.io/privacy) (TalkQTE sends no zero-retention or opt-out flag to ElevenLabs); Anthropic's [Commercial Terms of Service](https://www.anthropic.com/legal/commercial-terms) and its privacy center article on [how long API data is stored](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data); OpenAI's [Terms of Use](https://openai.com/policies/terms-of-use); and the [Gemini API Additional Terms of Service](https://ai.google.dev/gemini-api/terms). No provider's retention is stated here as fact.

Show a transcript's expiry before a meeting starts. Keeping notes must not silently keep the entire transcript. If a saved note contains a selected quote, make clear that the quote is retained with the note.

Expired data must be unavailable to search, prompts, exports, and integrations, even before physical cleanup runs. Run cleanup at startup and periodically while the app is open. Do not claim that deletion has erased copies in OS backups or existing exports.

A private-session option should discard its transcript and temporary analysis when the session ends, retaining only items the user explicitly saves. Deletion must cover indexes, temporary files, cached snippets, and derived data.

## Screen sharing
