# Privacy design

TalkQTE is an early desktop prototype with an optional microphone activity check. TalkQTE does not transcribe on this Mac or offer a local Whisper option. With your own Deepgram and Anthropic API keys stored, any build, ordinary and release builds included, can stream a live session's audio to Deepgram and send transcript lines to the Anthropic API for cue decisions, only after that session's in-app processing review is approved. Without both keys an ordinary build has no live transcription and says which key to add. Development cue backends and token files are described below. It is not a released meeting recorder. Current behavior and future requirements are separated below.

## Current prototype

- The app has no demo and plays no bundled dialogue; cues come only from a live session's transcript. There is no system-wide audio capture. On macOS any build, release builds included, can capture one application's audio when you choose that application for a live session, as described below; nothing else on the Mac is captured. There is no speech model, TalkQTE account system, or telemetry integration, and no cloud cue model except the Anthropic API with your own key and the development connections described below. Audio and transcript lines leave this Mac only to Deepgram and Anthropic, with your keys or a developer's, after you approve the session's review. TalkQTE does not transcribe on this Mac and no longer downloads a speech model. A model that a build before 16 November 2026 downloaded stays in the app's data folder (`~/Library/Application Support/com.talkqte.desktop/models/`); the app no longer reads or deletes it, and you can delete that folder yourself.
- The macOS app can separately monitor activity from the default microphone after an explicit start action and operating-system permission. It processes samples only to produce a coarse quiet/active indicator. Samples are not retained, recorded, logged, uploaded, or sent to the interface. It detects signal level, not speech, meeting participation, or the other side of a call.
- Monitoring starts off. Stop releases the input device on a worker, with a stopping state until release finishes; restarting is blocked during cleanup. A pending permission result cannot restart a cancelled session. Monitoring does not automatically restart or switch devices after an error. Hiding the companion does not stop microphone monitoring; only a live session's own microphone use ends with the session. Use Stop microphone or quit the app.
- A live session needs a cue connection (your Anthropic key, or a development `claude-cli` or lab connection) and a Deepgram credential (your key, or a development token file), described next; without them a build has no live transcription and says which key is missing. It starts only when you choose **Start live session**: with the microphone (once the operating system grants microphone access), with one application you choose, or with both, as described below. Microphone samples pass through a bounded in-memory buffer and, once you have enabled cue processing for the session, are streamed to Deepgram; until then they are discarded. TalkQTE does not write them to disk or log them. The recognized text feeds the phrase-based questions. It stays in memory until you start another session or quit (the `timing-log` development build below also writes it to a file), and it is exported only if you choose: export is refused while a live session runs, and after it ends the export holds your notes only unless you tick **Also keep this meeting** in the export review for that session, which adds the transcript and the cues shown. Stop, in either window, releases the microphone, sends the last captured audio, waits up to 10 seconds for the last results, and ends the session; the session also ends if microphone access is refused, the device fails, or transcription stops. Quitting discards queued audio. Both windows see the live cue and its source line; the companion can stop the session but not start it. Without the `native-audio-spike` development feature, other apps' audio is not captured.
- Live sessions are transcribed through Deepgram with your own Deepgram API key from the Keychain ([provider keys](docs/provider-keys.md)), at most 120 minutes of audio per session (no per-launch or per-day cap), billed to your Deepgram account. Instead, a debug build with the `cloud-transcription` feature, which `lab-evaluator` switches on and which no default or release build includes, can be pointed before launch at `TALKQTE_DEV_STT_BACKEND=deepgram`, the path of an owner-only file holding a short-lived Deepgram token, and a cap of 1 to 60 minutes of audio for the whole launch, across sessions and sources; that development selection wins over a stored key. **When:** nothing is sent until you approve cue processing for the session in the app, whose review names Deepgram as the audio destination, what is sent and the cap; a launch setting cannot approve it. Until then captured audio is discarded and nothing is transcribed, and audio captured before the approval is never sent. **What:** the audio of the capture sources the session was started with, and only those, which the review names: the microphone, one selected application's audio (all of its windows may be included), or both as two streams that share the session's one minute cap; as 16 kHz mono PCM, with the key or token in a request header. An application can join only a session started with it. Notes, names, focus lines and the transcript are not sent to Deepgram. **Request settings:** every request carries `mip_opt_out=true`, asking Deepgram to opt out of its Model Improvement Program, and asks for Nova-3 transcription in the language chosen in Settings before the session (English by default, or Multilingual, which Deepgram bills at a higher rate), with punctuation and speaker labels; the speaker labels are never shown or sent to a cue model, and only the `timing-log` build records them. In a session with both sources, TalkQTE labels each line "You" (microphone) or "Them" (application) by where it was heard, not who spoke; these labels stay on the Mac (the cue model still receives a fixed "Speaker"), and a microphone line that closely copies one application line (a likely echo through the speakers) is never sent to a cue model; it stays in the transcript, marked, and in a kept meeting marked the same way, unless you remove it. **Ending:** turning cue processing off, the end of a lab cue run (including Pause in the lab), the launch's cap, a refused key or token (a refused key is then shown as rejected), an exhausted account, rate limiting or a lost connection stops sending and ends the session with a plain reason, with no fallback to another transcription service and no retry. Stop sends a microphone session's already-captured audio and waits up to 10 seconds for the last results; an application-audio session, End and quit close the stream at once. **What is kept:** TalkQTE writes no audio, key or token to disk. Deepgram handles the audio under the key holder's Deepgram terms, and TalkQTE cannot recall audio once sent ([details](docs/cloud-transcription.md)).
- **Another application's audio (macOS).** Before a live session you can choose, under **Listen to**, the microphone, one application, or both. Nothing about other applications is read until you choose an application option, read the notice (audio from all windows of that application may be included) and choose **List applications**: TalkQTE then asks macOS once for the running applications, which can bring up the macOS Screen & System Audio Recording prompt, and shows their names in the notebook only (the notebook also receives each one's bundle identifier, to match an application by identity); they stay on the Mac. Only the one application you pick is captured, through ScreenCaptureKit with audio only (TalkQTE registers no screen or video output and keeps no picture), and only from when the session starts until Stop, the application ending, or a failure. Its audio is treated like the microphone's: discarded until you approve the session's review, which names it, then sent to Deepgram as a second stream under the same cap, never written to disk. TalkQTE cannot see which windows of the application make sound, so a browser's other tabs may be included. Once a source exists, the notebook shows its status under **Cue processing**, including when it may still be capturing, with a Stop for it. A development build with the `native-audio-spike` feature, which no release build includes, adds launch settings for unattended fictional lab runs: `TALKQTE_DEV_APPLICATION_SOURCE` names an application exactly and stands for the acknowledged notice (the app lists once and starts a session from it alone; a missing match or refused permission starts nothing and is not retried), `TALKQTE_DEV_APPLICATION_WITH_MICROPHONE=1` declares it for the next microphone session the person starts, and `TALKQTE_DEV_STOP_AFTER_S` asks the ordinary Stop later. None of this has been run on a device ([details](docs/native-application-audio-host.md)).
- **When a call starts (off by default).** If you turn on **Settings → When a call starts**, TalkQTE reads once a second, while it is open, whether another app is using your default microphone (a Core Audio property; the microphone is not opened) and which app is frontmost (its name and bundle identifier). It never reads audio, window titles or screen content, and this stays on the Mac: the companion gets only an offer naming the app. The offer starts nothing; Start opens the notebook's ordinary start and approval. Nothing is read while the setting is off, and it, "Not for this app" and "Don't ask again" last until you quit ([details](docs/call-prompt.md)).
- A development build with the `claude-cli` feature, which no default, release or `native-audio-spike` build includes, can send conversation lines off this Mac to Anthropic for cue decisions. That is hosted processing, through the Claude Code CLI installed on this Mac and your own signed-in Claude subscription. It exists for the owner's own development use and is not a product feature.
  - **When.** Nothing is sent until you review and turn on **Cue processing** for the session, except in a debug build with both `claude-cli` and `native-audio-spike` when the developer explicitly sets `TALKQTE_DEV_MODEL_CONNECTION=on` at launch. That setting approves recent and new conversation only, never prior notes, for each live session in that launch; the panel discloses it. These builds cap requests per session at 100 by default, adjustable down with `TALKQTE_DEV_MODEL_CALLS`; Off/On and Pause/Resume do not reset the count. Invalid launch settings leave cues off. See [launch consent](docs/real-app-lab.md#model-connection-without-clicks). After that, a request goes after each new transcript line, at most once every two seconds and one at a time. Sending ends when you turn it off, stop the session or quit, or when a failure stops it; quitting, Ctrl-C or a terminal hang-up ends any request on its way and any helper it started. The notebook says while lines are being sent, and the companion shows a cloud while the connection is on, with an arrow while a request is on its way.
  - **What.** Each request holds up to six recent transcript lines and any lines the cue on screen cites, the cue on screen, up to four earlier cues with how each ended, and your session name if you set one. Because a request follows each new line, over a session nearly every transcript line is sent, a few at a time.
  - **Never sent.** Audio, the full transcript in one request, notes you type, imported or Granola notes (the review does not offer them), focus lines and device names.
  - **Refusals.** The app refuses to start the CLI when the environment carries an API key, provider switch, gateway or proxy setting, so nothing is billed through an API.
  - **Failures.** Any failure stops sending for the session and shows why. A single slow reply is skipped, and two in a row stop sending.
  - **What Anthropic keeps.** What is sent is handled under your Claude account's terms and settings. The CLI runs with session persistence off, which does not remove the provider's own retention, and lines already sent cannot be recalled ([design](docs/cue-model.md)).
- A development build with the `timing-log` feature, which no default, release or `native-audio-spike` build includes, can write a timing log for lab runs with fictional audio. It writes only when the developer sets the `TALKQTE_TIMING_LOG` environment variable to a file outside the repository, and then records every session until the app quits, microphone sessions included. Each line holds its time and one of: a session starting or ending, with the build's commit and features; a chunk of audio handed to transcription, with its timing and whether it was silent, never the audio itself; a recognized line with its speaker label and full text; or a cue decided, sent to the companion or cleared, by its id and kind. With a model connection it also records the connection turning on or off, with its backend, model, effort and whether approval came from review or the launch setting; a session cap stop as `evaluation_stopped` with failure `call_limit`; each request, by number, with the last line covered and how many lines were sent; and each result, with its outcome, latency and a fixed failure code. The prompt and the raw reply are never written. A cue the model proposed is written by its id, not its words, and a request ended by Stop, Pause or turning the connection off is written as cancelled. A cue's question and source line are written only for a phrase cue raised by a transcript line. A cue that quotes an imported or Granola note, lists the focus lines or concerns them is written without its question, note or focus text. The file is created readable by its owner only, is only appended to, and nothing is sent anywhere ([details](docs/real-app-lab.md#timing-log)).
- TalkQTE does not tell other people that their voices are being captured and does not collect anyone's consent. A live session's microphone can pick up anyone speaking near it. When you choose an application for a session, TalkQTE captures that application's audio, from all of its windows (for a call app, every participant you hear in it; for a browser, possibly other tabs too), so other participants are heard that way. When cue processing is on, the speech of anyone the microphone or the chosen application picks up is sent to Deepgram, a third-party service; TalkQTE does not prompt you to tell them. If anyone else may be heard, telling them and obtaining any consent your local law requires is your responsibility.
- What TalkQTE never captures: video, screenshots or any picture of the screen (it registers audio output only with ScreenCaptureKit), any application you did not choose for the session, the whole system's audio, and its own output. It installs no audio driver.
- The optional name and focus lines in Settings are kept in process memory for the session and cleared when the app quits. They are excluded from Markdown export. The name may be sent with conversation only after the cue-processing approval described above or below; focus lines are not sent to the cue provider. They are not sent to the companion as settings fields (it learns that a question is about the focus, and a Still open list names the focus lines not yet discussed).
- Prior notes you import from a file you choose are read once into memory while you choose, and released when you import, cancel, or close the chooser; only the notes you tick are kept, for this session, listed in the notebook's **Prior context** section, which is closed until you open it, and labeled as not from the conversation. Remove deletes the imported copy and clears any current reminder quoting it, including a reminder held open for reading. A note may be shown once as a reminder in the companion when the conversation uses words from its title, labeled as coming from your notes; that happens on this device only. Imported notes are excluded from Markdown export and are not persisted by TalkQTE. They stay on this device unless you explicitly approve the selected-context development API export described next; nothing reads a file you did not pick.
- The development API lab can explicitly select `selected-prior-v2` context. Only after the session review approves exact stored note snapshots can it send their excerpts, titles, source labels, dates and opaque snapshot versions, together with approved conversation, the optional session name and current/earlier cues, to the Anthropic API. Importing or selecting a note is not processing permission. Saved snapshots are not verified current. Approving zero notes sends none, using the same selected-context prompt and route. Default API, subscription and standalone CLI paths still exclude prior notes; this mode sends no audio, manual notes or focus lines to the cue provider. The review names API billing, the per-run cap, request limits, retention and any separate transcription destination. Changing or removing an approved note invalidates its grant and pending/held cue evidence; Off and Stop prevent future requests and reject late replies but cannot recall content already sent. This is a separately enabled fictional lab path, not real-account or live-usefulness acceptance ([scope and remaining gates](docs/selected-context-lab-opt-in.md)).
- Your own provider keys: **Settings → Your API keys** stores one Deepgram API key and one Anthropic API key, which you create in your own accounts. They are kept only in your macOS login Keychain (service `app.talkqte.provider-key`), never written to a file, never logged and never shown again; the notebook only learns whether each key is set, has been checked, or was rejected. Storing a key sends nothing. **Test** sends one read-only request to that key's provider (Deepgram's project list, Anthropic's model list), which neither transcribes nor generates anything. **Remove** deletes the key from the Keychain. The Deepgram key is used for transcription and the Anthropic key for cue decisions, as described below. See [provider keys](docs/provider-keys.md).
- Cue decisions with your own Anthropic key: once you approve the session's review, which names the Anthropic API beside Deepgram, the app sends the Anthropic Messages API up to six recent transcript lines (labelled only `Speaker`) and any lines the cue on screen cites, the cue on screen, up to four earlier cues with how each ended, and your session name if you set one. It sends after new lines, at most once every two seconds, at most 400 requests and an estimated $0.50 per session, with the key only in a request header. The caps are per session; there is no per-launch or per-day cap. Pause cues stops these requests but not the audio to Deepgram, which is still sent and billed until you turn processing off or stop the session. It never sends audio, the full transcript, your notes, imported notes or focus lines. Anthropic bills your account and handles what is sent under your API account's terms; lines already sent cannot be recalled. A refused key, a rate limit, a failure or a cap stops cues for the session with a plain reason; nothing falls back to another service and nothing is retried. The request count and spend estimate stay in memory ([details](docs/own-key-cues.md)).
- Meeting notes with your own Anthropic key: after a live session has ended, **Write meeting notes…** in the notebook can ask the Anthropic Messages API, once for that meeting, to write a summary, decisions, action items and open questions. This is separate from the session's processing review, which ended with the session, and nothing is sent until you confirm a second time. Before you confirm, the notebook shows what will be sent (the session's whole transcript, with each line's time from the start and no speaker labels, and your own notes only if you tick **Also send my notes**, off each time), to whom (the Anthropic API, US, with your key, billed to your account), its size, and an estimated cost with its worst case. The session name, focus lines, imported or Granola notes, the cues shown and audio are never sent for notes. One request per meeting, with no retry and no other model or service; a transcript beyond 4,000 lines or 240,000 bytes is refused before sending, and so is any request whose worst-case estimate (one token per byte) passes $1.00. The request sent is exactly the one the confirmation described; if the transcript, your notes or the notes setting change first, it is refused and shown again. **Stop waiting** before the request leaves sends nothing. The reply is checked: every item must cite lines that were sent, and an owner or date is shown only when those words appear in the lines the item cites. Notes that fail a check are shown as failed, not repaired. Those checks do not make the notes true: a model can still write an item that is invented or misleading, including from words someone said in the meeting to steer it, so check each item against the lines it cites. Links, images and HTML in the model's text are removed or escaped before you see it, so the export loads nothing from it. The notes stay in memory: they reach a file only if you keep them and then export, and the next session clears them. Anthropic handles what is sent under your API account's terms, and it cannot be recalled ([details](docs/meeting-notes.md)).
- Connecting Granola is your choice, in the desktop app only. The sign-in happens in your browser with Granola; the app receives an access token through a one-time return address on this Mac and keeps it in memory, never on disk. Disconnect invalidates all copies of the connection without waiting for the network and discards delayed results, even after a new connection opens. Idle credentials are dropped immediately; an already-running request may finish before its credentials and response are dropped. Disconnect also cancels pending sign-in. Imported copies remain until you remove them. With that token the app asks Granola's documented MCP server for your note list, for the notes you tick, and, if you press **Suggest from Granola**, one fixed question to its assistant; nothing else: no transcripts, no writing back, no other account data. Granola sees the sign-in and those requests, with a `TalkQTE` user agent. The notebook shows whether a connection is open, which tools the server offers, and, for notes you kept, whether an update check is available and the result of the last one; it never shows whose account it is. An update check runs only when you press it and asks again only for notes you already kept; it is not offered for a Granola connection today, so no such request is sent. The suggestion step sends only that fixed question; Granola's model answers from notes it already holds, the answer is shown for you to tick, and only the lines you add become focus lines on this device. No transcript, note, or focus line of yours is sent by that step.
- The optional `TALKQTE_GRANOLA_TRACE` developer diagnostic prints bounded structures to stderr: known field names, string lengths, collection sizes, and a tag outline. Arbitrary JSON keys, scalar values, tool descriptions, and schema defaults are masked; raw tool schemas are not logged. Your terminal may retain this output. The diagnostic is off unless explicitly enabled; it is not an automatic upload or a guarantee about provider or operating-system logs.
- No cue is written to your notes. A quoted line, like any other cue, is shown and then let go, whether you hold it, dismiss it or leave it. The **Keep this line** button, which appended a quoted sentence to your notes, was removed on 14 November 2026.
- The transcript and your notes live in process memory. Dismissed or expired questions are let go; nothing keeps them as notes or action items. Starting or stopping a live session keeps notes. Quitting the app clears everything. There is no database, recovery, retention scheduler, or encrypted notebook.
- A Markdown export is the only implemented persistence. You review the generated text, then choose the file destination in a native save dialog. The saved file contains exactly that preview. By default it holds your notes only: no transcript, cue, name, focus line or imported note. For an ended session you may tick **Also keep this meeting** in the review, off for every new session, to add that session's transcript (times from the start, no speaker labels) and the cues it raised from the conversation, each with the transcript line it quoted. Reminders quoting an imported note and the Still open list of your focus lines are left out, so no imported-note content, focus line or session name setting is written; words people said aloud, names included, are in the transcript; the preview updates before you choose a destination, and nothing is written until you do. Meeting notes written with your key (above) are added after your notes only if you chose **Keep with this meeting**, as you edited them. Export itself makes no model call; there is no automatic saving and no background file. The destination may be a folder synchronized by other software; exported files are outside TalkQTE's control.
- The floating window receives only the current question, its source excerpt, and the state needed to display it. It cannot write to or edit your notes, and it cannot export.
- Both windows receive microphone status, coarse activity and a bounded display name for the opened input, without samples, device identifiers or precise levels. The input name is read only after an explicit start and microphone permission, kept in memory for that stream, and displayed beside microphone status in the notebook/Settings. It is never written to notes, exports, logs or provider requests. It clears from status on release or error. Only the main window can start monitoring; the companion can stop it. The browser preview never requests microphone permission.
- The app has no automatic upload feature. The development server uses loopback connections, and installing dependencies requires network access. The browser preview downloads exports through the browser and is not a separate production service.

Do not use this prototype for real or sensitive meeting data. Closing the app loses unsaved notes, and there is no implemented storage protection beyond the operating system's process boundaries. The owner has reported a bounded activity-monitor acceptance check; device-specific disconnect/recovery details and the separate cloud-transcription path still need native verification. See the [acceptance record](docs/native-validation.md#owner-reported-microphone-acceptance--11-november-2026); synthetic tests do not prove those platform behaviors.

## Optional fictional development lab

The [Claude cue lab](docs/claude-cue-lab.md) is a separate, explicitly invoked development script. A selected bundled fictional scenario is sent to Claude through the user's subscription; this is hosted processing. It has no microphone, live transcript, arbitrary-file input, or connection to the desktop engine. Listing cases, dry runs and offline tests do not invoke a model. A [bounded batch](docs/cue-simulation.md) sends each selected fictional case the same way, one request at a time, only when explicitly run with a call cap. The timing simulation sends lines of a bundled fictional conversation the same way, under the same flags: up to 100 requests in one invocation, each with up to six recent lines, the lines the cue on screen cites, that cue's text, the fictional listener's name, and the text of up to four cues shown earlier in the same conversation; cue text may be text the model wrote in an earlier reply. The lab's recorder sends nothing anywhere: it plays a results file of a bundled fictional conversation in the browser preview on the same device, speaks the lines with the system's own voices, and writes its videos to a directory the user names outside the repository. A separate, optional voice step can instead send the lines of a bundled fictional conversation to OpenAI's text-to-speech service to make more natural synthetic voices; it runs only when explicitly started with a character cap and the user's own key, and sends nothing but those fictional lines, a preset voice name and speaking instructions. The lab's [meeting emulator](docs/meeting-emulator.md) plays only fictional conversations and sends nothing anywhere; its window-only recorder records just the emulator's window and the TalkQTE companion's window with the emulator's sound, never the whole screen, needs the Screen & System Audio Recording permission, and writes outside the repository. A second optional step can send descriptions of invented people, naming no one, to OpenAI's image service to make portraits for the mock call, under the same conditions.

The [dialogue lab](docs/cue-dialogue.md) generates fictional conversations in which a simulated listener responds to cues. Its dry run and offline runs, with deterministic fakes, send nothing anywhere. A model run, which has not yet been made and needs the owner's go-ahead, sends each request to Anthropic through the same subscription sign-in and isolation, under one call cap of at most 300 for the whole run:

- **the generator**: a domain, a number and the counts of moments to write;
- **the other participants**: one generated fictional meeting's title and setting, the invented people's roles, goals and private facts, the listener's name and role, the transcript so far, whose turn it is and how many turns are left;
- **the listener**: the meeting, its own invented goal and facts, the others' names and roles, the transcript as it heard it, whether it has the floor, and the text of a cue card when one is shown and of cards it read earlier, which may be text the cue model wrote;
- **the cue evaluator**: what the timing simulation sends;
- **the judge**: the meeting's title and setting, the people's names and roles, the brief's criteria, and one transcript.

All of that text is invented by a model or by hand; no real conversation, file or note is read. The run writes its briefs, results, reviews and an event log holding every request and reply to a directory the user names outside the repository, and omits raw CLI output, session IDs, account identity and credentials.

The runner disables tools, customizations, MCP connections, and session persistence, uses a temporary working directory, and prints a filtered report to stdout. A batch or simulation also writes a results file and an event log to a directory the user names outside the repository; they hold the exact input of every request and every model decision, and omit raw CLI output, session IDs, account identity and credentials. It does not store a meeting archive or extract credentials. These controls do not establish zero provider retention or prevent all CLI diagnostic/account state. Review the CLI and provider settings independently before any future work with real content. No such input path is implemented here.

## Requirements for meeting capture

- Capture begins only after an explicit action. Show whether the microphone, system audio, or both are active.
- Provide a visible pause/stop control and an accessible shortcut. Stopping capture releases the devices.
- Transcription (Deepgram) and cue decisions (Anthropic) use named cloud providers only after the person turns them on for that session. They are off by default and can be turned off at any time. Every transcription request asks Deepgram to opt out of model improvement. Disclose which provider receives audio or text; provider handling and retention remain subject to that provider's terms. Nothing falls back silently to another provider. Audio and lines are sent only after the session's in-app processing review is approved. It has no local transcription option. A new processing choice needs its own review and acceptance.
- Without that consent a session has no transcription and no cues; there is no on-device transcription mode. No TalkQTE account or telemetry is needed.
- Keep credentials and personal data in application-managed storage outside the checkout. The frontend receives only the data it needs.
- Raw audio is held in a bounded memory buffer and not written to disk by default. Debugging must not silently create recordings or dump transcripts into logs.
- Sharing is explicit: show the destination and the exact content being exported. Integrations are off until enabled and scoped by the user.
- No private meeting data belongs in the public development repository, review services, demos, or CI artifacts.

Data kept on the device is not inaccessible to the device owner, an administrator, malware, or backups. Data sent to a provider is handled under that provider's terms, and TalkQTE cannot recall it. Do not describe local storage as encrypted until encryption is implemented and tested. Plan for protected storage and OS keychain-managed keys before recommending TalkQTE for sensitive meetings.

## Proposed retention defaults

These defaults remain open to product feedback:

| Data                                             | Proposed default                                                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| Raw audio                                        | Memory only in TalkQTE; sent to Deepgram while transcription is on, not kept by TalkQTE once sent |
| Full transcripts                                 | Delete after 30 days; offer session-only, 7 days, 30 days, and keep until deleted                 |
| Explicitly saved notes, decisions, and questions | Keep until the user deletes them                                                                  |
| Temporary analysis and search indexes            | Follow the retention of their source data                                                         |
| External exports                                 | User-controlled copies; local deletion cannot revoke them                                         |

This table covers only what TalkQTE keeps. What a provider keeps is set by its own terms: Deepgram's [terms of service](https://deepgram.com/terms), [privacy policy](https://deepgram.com/privacy) and [model improvement program](https://developers.deepgram.com/docs/the-deepgram-model-improvement-partnership-program), which every TalkQTE request opts out of; and Anthropic's [Commercial Terms of Service](https://www.anthropic.com/legal/commercial-terms), which govern use of its API, and its privacy center article on [how long API data is stored](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data). No provider's retention is stated here as fact.

Show a transcript's expiry before a meeting starts. Keeping notes must not silently keep the entire transcript. If a saved note contains a selected quote, make clear that the quote is retained with the note.

Expired data must be unavailable to search, prompts, exports, and integrations, even before physical cleanup runs. Run cleanup at startup and periodically while the app is open. Do not claim that deletion has erased copies in OS backups or existing exports.

A private-session option should discard its transcript and temporary analysis when the session ends, retaining only items the user explicitly saves. Deletion must cover indexes, temporary files, cached snippets, and derived data.

## Screen sharing

The desktop settings include a floating-window toggle. Choosing Hide removes the companion. The companion can also ask which edge of its window stays put (top or bottom), so it can draw its bar there; the answer comes from the placement preset and whether the window was dragged, and carries no conversation, notes or screen position. Capture exclusion is not implemented. Do not assume the overlay is invisible to screen sharing. Cross-app focus, Spaces, full-screen meetings, and different sharing methods still require native testing.

## Optional integrations

The prototype supports user-initiated Markdown export, selected file imports, and a development Granola connection.
