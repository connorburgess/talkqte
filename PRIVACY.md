# Privacy design

TalkQTE is an early desktop prototype with an optional microphone activity check and, in developer builds, an optional local live session. It is not a released meeting recorder. Current behavior and future requirements are separated below.

## Current prototype

- The demo plays bundled fictional dialogue and generates questions only from that text. It does not use microphone audio. Builds without the `native-audio-spike` development feature, including every default and ordinary `local-whisper` build, have no system-audio or other-application capture; that development build, described below, is the only exception. There is no bundled Whisper model, built-in cloud cue model, TalkQTE account system, or telemetry integration. A speech model is downloaded only on request, as described below.
- The macOS app can separately monitor activity from the default microphone after an explicit start action and operating-system permission. It processes samples only to produce a coarse quiet/active indicator. Samples are not retained, recorded, logged, uploaded, or sent to the interface. It detects signal level, not speech, meeting participation, or the other side of a call.
- Monitoring starts off. Stop releases the input device on a worker, with a stopping state until release finishes; restarting is blocked during cleanup. A pending permission result cannot restart a cancelled session. Monitoring does not automatically restart or switch devices after an error. Pausing or ending the demo and hiding the companion do not stop microphone monitoring; only a live session's own microphone use ends with the session. Use Stop microphone or quit the app.
- In builds with the `local-whisper` feature, Settings offers an optional speech model download. It starts only when you choose it, after showing the model's size and source. It makes HTTPS file requests to the whisper.cpp repository on Hugging Face, which may redirect to its download network, and resumes with further requests if a connection drops. Those hosts see your IP address and a `TalkQTE` user agent; no account, audio, transcript, or notes are sent. The file is kept in the app's data folder, installed only after its SHA-256 matches the value pinned in the app, and deleted by Remove model. Partial downloads are deleted on Cancel, on failure, and at the next launch.
- A live session exists only in builds with the `local-whisper` feature and an installed speech model. Without the `native-audio-spike` development feature it starts only when you choose **Start live session** and the operating system grants microphone access; a development build with that feature can also start one without the microphone, as described below. Microphone samples pass through a bounded in-memory buffer to a speech model running in the app process on this device; they are not written to disk, logged, or sent anywhere, and are discarded once transcribed. The recognized text feeds the same phrase-based questions as the demo. It stays in memory until you start another session or quit, and export is refused for a live session. Stop, in either window, releases the microphone, transcribes the last queued seconds, and ends the session; the session also ends if microphone access is refused or the device fails. Quitting discards queued audio. Both windows see the live cue and its source line; the companion can stop the session but not start it. Without the `native-audio-spike` development feature, other apps' audio is not captured.
- A development build with the `native-audio-spike` feature, which no default or ordinary `local-whisper` build includes, adds an unvalidated command that can list running applications, send their names to the main window, trigger the macOS Screen Recording prompt, feed one selected application's audio, including all of its windows, to the live session, and start a live session for that application alone without the microphone or its permission. Listing, choosing and starting an application are reachable only through that command; the notebook has no control for them. Once a source exists, the notebook shows its status under **Cue processing**, including when it may still be capturing, with a Stop for it, and the microphone row says that a selected application's audio may still be captured. It has not been run on a device ([details](docs/native-application-audio-host.md)).
- TalkQTE does not tell other people that their voices are being captured and does not collect anyone's consent. Without the `native-audio-spike` development feature, TalkQTE does not capture other participants through a call or another app, but a live session's microphone can pick up anyone speaking near it, and the development build above can capture a selected application's audio, which may include other participants. If anyone else may be heard, telling them and obtaining any consent your local law requires is your responsibility.
- The optional name and focus lines in Settings are kept in process memory for the session, are not sent to the companion window as such (it learns that a question is about the focus, and a Still open list names the focus lines not yet discussed), are never exported, and are cleared when the app quits.
- Prior notes you import from a file you choose are read once into memory while you choose, and released when you import, cancel, or close the chooser; only the notes you tick are kept, for this session, listed in the notebook's **Prior context** section, which is closed until you open it, and labeled as not from the conversation. Remove deletes the imported copy and clears any current reminder quoting it, including a reminder held open for reading. A note may be shown once as a reminder in the companion when the conversation uses words from its title, labeled as coming from your notes; that happens on this device only. Imported notes are never exported, written anywhere, or sent, and nothing reads a file you did not pick.
- Connecting Granola is your choice, in the desktop app only. The sign-in happens in your browser with Granola; the app receives an access token through a one-time return address on this Mac and keeps it in memory, never on disk. Disconnect invalidates all copies of the connection without waiting for the network and discards delayed results, even after a new connection opens. Idle credentials are dropped immediately; an already-running request may finish before its credentials and response are dropped. Disconnect also cancels pending sign-in. Imported copies remain until you remove them. With that token the app asks Granola's documented MCP server for your note list, for the notes you tick, and, if you press **Suggest from Granola**, one fixed question to its assistant; nothing else: no transcripts, no writing back, no other account data. Granola sees the sign-in and those requests, with a `TalkQTE` user agent. The notebook shows whether a connection is open, which tools the server offers, and, for notes you kept, whether an update check is available and the result of the last one; it never shows whose account it is. An update check runs only when you press it and asks again only for notes you already kept; it is not offered for a Granola connection today, so no such request is sent. The suggestion step sends only that fixed question; Granola's model answers from notes it already holds, the answer is shown for you to tick, and only the lines you add become focus lines on this device. No transcript, note, or focus line of yours is sent by that step.
- The optional `TALKQTE_GRANOLA_TRACE` developer diagnostic prints bounded structures to stderr: known field names, string lengths, collection sizes, and a tag outline. Arbitrary JSON keys, scalar values, tool descriptions, and schema defaults are masked; raw tool schemas are not logged. Your terminal may retain this output. The diagnostic is off unless explicitly enabled; it is not an automatic upload or a guarantee about provider or operating-system logs.
- **Keep this line** on a quoted cue appends that sentence, its time, and its speaker to your notes, which live in memory like everything else; untouched cues are never kept.
- The transcript and your notes live in process memory. Dismissed or expired questions are let go; nothing keeps them as notes or action items. Ending or replaying the demo, and switching between the demo and a live session, keep notes. Quitting the app clears everything. There is no database, recovery, retention scheduler, or encrypted notebook.
- A Markdown export is the only implemented persistence. You review the generated text, then choose the file destination in a native save dialog. The saved file contains exactly that preview, even if the demo advances while the dialog is open. The destination may be a folder synchronized by other software; exported files are outside TalkQTE's control.
- The floating window receives only the current question, its source excerpt, and the state needed to display it. Its only write to the notes is appending the quoted line it is showing when you choose Keep this line; it cannot edit notes otherwise or export.
- Both windows receive microphone status, coarse activity and a bounded display name for the opened input, without samples, device identifiers or precise levels. The input name is read only after an explicit start and microphone permission, kept in memory for that stream, and displayed beside microphone status in the notebook/Settings. It is never written to notes, exports, logs or provider requests. It clears from status on release or error. Only the main window can start monitoring; the companion can stop it. The browser preview never requests microphone permission.
- The app has no automatic upload feature. The development server uses loopback connections, and installing dependencies requires network access. The browser preview downloads exports through the browser and is not a separate production service.

Do not use this prototype for real or sensitive meeting data. Closing the app loses unsaved notes, and there is no implemented storage protection beyond the operating system's process boundaries. The owner has reported a bounded activity-monitor acceptance check; device-specific disconnect/recovery details and the separate local-transcription path still need native verification. See the [acceptance record](docs/native-validation.md#owner-reported-microphone-acceptance--11-november-2026); synthetic tests do not prove those platform behaviors.

## Optional fictional development lab

The [Claude cue lab](docs/claude-cue-lab.md) is a separate, explicitly invoked development script. A selected bundled fictional scenario is sent to Claude through the user's subscription; this is hosted processing. It has no microphone, live transcript, arbitrary-file input, or connection to the desktop engine. Listing cases, dry runs and offline tests do not invoke a model. A [bounded batch](docs/cue-simulation.md) sends each selected fictional case the same way, one request at a time, only when explicitly run with a call cap. The timing simulation sends lines of a bundled fictional conversation the same way, under the same flags: up to 100 requests in one invocation, each with up to six recent lines, the lines the cue on screen cites, and that cue's text, which may be text the model wrote in an earlier reply. The lab's recorder sends nothing anywhere: it plays a results file of a bundled fictional conversation in the browser preview on the same device, speaks the lines with the system's own voices, and writes its videos to a directory the user names outside the repository. A separate, optional voice step can instead send the lines of a bundled fictional conversation to OpenAI's text-to-speech service to make more natural synthetic voices; it runs only when explicitly started with a character cap and the user's own key, and sends nothing but those fictional lines, a preset voice name and speaking instructions.

The runner disables tools, customizations, MCP connections, and session persistence, uses a temporary working directory, and prints a filtered report to stdout. A batch or simulation also writes a results file and an event log to a directory the user names outside the repository; they hold the exact input of every request and every model decision, and omit raw CLI output, session IDs, account identity and credentials. It does not store a meeting archive or extract credentials. These controls do not establish zero provider retention or prevent all CLI diagnostic/account state. Review the CLI and provider settings independently before any future work with real content. No such input path is implemented here.

## Requirements for meeting capture

- Capture begins only after an explicit action. Show whether the microphone, system audio, or both are active.
- Provide a visible pause/stop control and an accessible shortcut. Stopping capture releases the devices.
- Transcription runs locally with Whisper. No account, cloud transcription, telemetry, or automatic upload is needed for the initial version.
- Keep model files and personal data in application-managed storage outside the checkout. The frontend receives only the data it needs.
- Raw audio is held in a bounded memory buffer and not written to disk by default. Debugging must not silently create recordings or dump transcripts into logs.
- Sharing is explicit: show the destination and the exact content being exported. Integrations are off until enabled and scoped by the user.
- No private meeting data belongs in the public development repository, review services, demos, or CI artifacts.

Local processing does not make data inaccessible to the device owner, an administrator, malware, or backups. Do not describe local storage as encrypted until encryption is implemented and tested. Plan for protected storage and OS keychain-managed keys before recommending TalkQTE for sensitive meetings.

## Proposed retention defaults

These defaults remain open to product feedback:

| Data                                             | Proposed default                                                                  |
| ------------------------------------------------ | --------------------------------------------------------------------------------- |
| Raw audio                                        | Memory only; discard after transcription                                          |
| Full transcripts                                 | Delete after 30 days; offer session-only, 7 days, 30 days, and keep until deleted |
| Explicitly saved notes, decisions, and questions | Keep until the user deletes them                                                  |
| Temporary analysis and search indexes            | Follow the retention of their source data                                         |
| External exports                                 | User-controlled copies; local deletion cannot revoke them                         |

Show a transcript's expiry before a meeting starts. Keeping notes must not silently keep the entire transcript. If a saved note contains a selected quote, make clear that the quote is retained with the note.

Expired data must be unavailable to search, prompts, exports, and integrations, even before physical cleanup runs. Run cleanup at startup and periodically while the app is open. Do not claim that deletion has erased copies in OS backups or existing exports.

A private-session option should discard its transcript and temporary analysis when the session ends, retaining only items the user explicitly saves. Deletion must cover indexes, temporary files, cached snippets, and derived data.

## Screen sharing

The desktop settings include a floating-window toggle. Pausing the demo collapses the question into a compact paused companion; ending the demo or choosing Hide removes the companion. Capture exclusion is not implemented. Do not assume the overlay is invisible to screen sharing. Cross-app focus, Spaces, full-screen meetings, and different sharing methods still require native testing.

## Optional integrations

The prototype supports user-initiated Markdown export, selected file imports, and a development Granola connection. Imported context is excluded from the generated export; Granola reads are limited to listing, selected notes, and the fixed assistant question requested by the user. Sign-in/listing/suggestions have worked in account checks; the owner reported successful native note import and removal on 11 November. That basic observation does not establish account traffic, provider retention or secure deletion. Future calendar access should be read-only and calendar-scoped. Any future MCP interface should expose only user-selected meetings and tools. Sending notes to an external model or service changes where those notes are processed and must be disclosed before connection.

Granola disconnect and removal are separate controls; disconnect does not revoke consent at the provider or delete original notes. Later connections must likewise let users select the content and direction of transfer. Show retention choices for imported copies; deleting a TalkQTE copy must not silently delete its original in another app. Disconnecting must stop future access and offer a separate choice to remove imported data. Exported copies remain subject to the destination's access and retention rules.

The [Granola privacy checks](docs/granola-import-validation.md#privacy-boundary-checks) record fictional regression coverage and the remaining account-level acceptance. They do not establish provider retention or secure erasure from process memory.
