# Cue intelligence and feedback

Status: evaluation plan with an optional [fictional Claude Code lab](claude-cue-lab.md), 8 November 2026. No reasoning model is connected to the app, and no production provider, conversational feedback system, or learning pipeline is selected. This supports the [participation goal](../PRODUCT.md#goal-and-first-proof) and [product readiness plan](product-readiness.md).

## What powers the prototype today

Rust's `suggest` function in `src-tauri/src/engine.rs` matches a few phrases in bundled fictional dialogue and returns fixed questions. It also raises an "Open question" cue quoting a sentence that ends with a question mark and opens with a group-addressing phrase ("Does anyone…", "Any thoughts…", "Who can…"), only when no fixed question matched the line, under the same expiry and pause as the fixed questions, and with its two-minute repeat rule keyed to the question text so an unrelated question is not hidden. A recognized owner, date, or choice later withdraws it, and a line that answers its own question raises nothing. Questions about the call itself ("Can anyone hear me?", "Who can see my screen?") are excluded by a short word list, so any question containing one of those words ("call", "screen", "audio", …) is skipped even when it is about the work. Questions put to one person by name, questions in other words, and transcripts that drop the question mark are missed, and in a live transcript the rule cannot tell the user's own question from someone else's. Rust also controls timing, hold, cooldown, and dismissal. A second fixed rule set withdraws an open question when a later sentence names an owner (“Jordan will take it”, where the owner is “I” or a capitalized name), a deadline (“by Friday”, “tomorrow”), or a choice (“let's go with the sign”). Sentences that end with or open like a question, or contain a negation or hedge such as “not” or “maybe”, never count; a missed answer only leaves the question up until it expires. A question the user is reading stays in place and is marked as answered, with the answering line as a source. The same question type is not shown again within two minutes of when it was last raised and shown, so a repeated trigger does not re-ask a question the user has just seen. A question withdrawn before it was ever shown does not count. A sentence that opens by changing the topic, such as "Moving on to the budget", "OK, next item", or "On another note", withdraws an unread question as stale. A question being read stays, and its repeat history is kept. Otherwise the repeat history starts afresh for the new topic, and the same line can raise a new question; if it raises none, the usual pause follows the withdrawal. The phrase must open the sentence, so "Before we move on…" or "The trucks are moving on Tuesday" do not count, and moving to the next slide or page is not a topic change. Questions, negations, and hedges do not count either. A topic change described in other words is missed. An explicit correction that opens a statement as its own clause ("Sorry, I misspoke.", "Scratch that, …", "Correction: …", "I take that back", "Never mind —") withdraws an unread question only when that question came from the same speaker's line just before, within 10 seconds; the engine cannot tell what else a correction refers to, so it leaves any other question alone. Live transcripts label every line "Speaker", so there any speaker's correction right after the line counts. Words taken back earlier in the same line raise no question, including a question asked of the user, while what follows the correction still can. A question being read stays, and so does an "Asked you" question, which the user may still want to answer. The usual pause after a withdrawal applies, but unlike a topic change the repeat history is kept. A bare "Actually", a phrase that runs on ("Never mind the cost"), and a correction said without such a phrase are not recognized; the last is the `context-corrected` case below. When imported notes are present, a line that contains at least two distinctive words (five or more letters) from a note's title raises a "Context" reminder once per note per session: the companion shows the note's title and excerpt labeled with its date and "not from this conversation", lowest in priority and under the same expiry and pause as a question, so dismissing a reminder leaves the same pause before the next cue. Common meeting and function words never count, words with an apostrophe ("Robin's") never count, titles with many words need three matches, and words taken back or put to someone else by name do not count. This is a title-word match, not a judgment of relevance; it exists to test the context-reminder hypothesis in the [research notes](research.md#the-next-experiment) and the pilot comparison, which measure such reminders separately from clarification questions. The engine can also hold a session-only user name. A question with that name opening or closing the sentence ("Robin, can you take the draft?", "Hey Robin — could you…?", "What do you think, Robin?") becomes an "Asked you" cue showing the question. It counts as a question only if it ends with a question mark or opens with a question word after the name, so "Robin, the draft is done." stays quiet. It replaces an unread suggestion and ignores the cooldown, but not a question being read. It stays for 45 seconds instead of 18 so the user can answer. A topic phrase does not clear it, and only a newer direct question replaces it. Dismiss still works. The app shows no countdown, answer, or score. Questions naming someone else, or no one, do not become "Asked you". Once the user has set their name, a sentence that puts a question to someone else by name, such as "Alex, can you take the first draft?" or "Can someone take it, Alex?", raises no suggestion: it is theirs to answer and already says who is meant. Other sentences in the same line still can. A name here is one capitalized word set off by a comma; greetings, common openers ("Honestly,"), time words, months, words for a group that includes the user ("Everyone,"), and any word that could be the user (either part of "Sam Lee", or "Sammy") do not count. It matches on capital letters, so some matches will be wrong: "Budget, someone can take it?" is treated as addressed to someone. A question to the user by first name only, when Settings holds a full name, raises an ordinary suggestion rather than "Asked you". Two-word names, names a transcript writes in lower case, and names set off by a dash are missed, which leaves the line treated as before. Without a name set, nothing changes. The name is entered in Settings and kept only for the session; the demo script never addresses anyone by name, so this applies in live sessions. These are phrase matches, not judgments of meaning: paraphrased answers are missed, and some matches will be wrong. The browser preview has a separate simulation. Neither runs a language model or judges whether a cue was used. Whisper is planned for transcription, not cue reasoning, and is not installed in the meeting pipeline.

A one-line meeting goal set in Settings (9 November 2026) lets a question through the pause that follows another cue, under either timing setting, and keeps it for 45 seconds, the length given to a question asked of the user by name (a topic change or correction still withdraws it, and a question being read is never replaced), when the line uses at least two of the goal's identifying words (five letters or more, not common meeting words; three when the goal has more than six). The goal is the first thing besides the user's name that changes a lifecycle decision; it is a word match on the user's own words, not a judgment that the line serves the goal, and the companion is told only that the question is about the goal.

## The decision we want intelligence to help with

Use recent, source-linked context to decide whether assistance is still useful. Staying quiet is a valid result. Generate or display a cue only when it has an identifiable purpose and supported context; do not turn every ambiguity into an interruption.

- Suppress candidates already answered, duplicated, off-topic, superseded by transcript revisions, or too late to help.
- Re-evaluate after meaningful conversation changes instead of repeatedly sending the entire meeting on a fixed timer.
- Distinguish “someone asked a similar question” from “the issue is resolved.” An asked question may still be unanswered.
- Withdraw or mark resolved evidence when appropriate without replacing the text mid-read. Preserve manual dismissal and pause. A hold controls reading time, not whether a known-wrong claim remains valid.
- Abstain when sources, speaker attribution, or context are insufficient. Keep uncertainty visible in evaluation records.

Keep deterministic lifecycle and permission checks in Rust. A proposed semantic evaluator can return a bounded decision, a short cue if needed, and supporting source IDs. Validate that sources exist and the response matches the expected shape. The model must not control capture, export, file access, or external tools. Compare this design against simple rules before adding it to the live path.

## Learn from the conversation without a Save step

The ongoing conversation can provide possible outcome signals: a similar question was asked, an answer appeared naturally, a participant corrected the context, or the topic moved on. Use those signals first to manage the current session. With uncertain speaker identity, do not label a cue as used by the user.

Keep **observed use**, **resolution**, and **usefulness** distinct. A question can be repeated without helping; a reminder can help someone stay grounded without being spoken; a dismissed cue can have been useful already. Neither silence nor dismissal is an automatic negative training label. Similar speech does not prove that TalkQTE caused it.

Optional, low-effort feedback such as helpful, wrong context, or too late can supplement observed signals, but should not interrupt the call. Compare inferred outcomes against human labels in fictional scenarios before trusting them. Measure missed useful opportunities and incorrectly suppressed cues as well as displayed-cue precision.

Session adaptation, durable personal preferences, and training a shared model are separate decisions. Begin with bounded in-memory context. Persisting outcomes, uploading transcripts, or training on conversations is not implied by using a cue or connecting a note-taker. Follow [PRIVACY.md](../PRIVACY.md) and make any later retention/processing choice explicit. An unused cue should not become a meeting note or action item.

The [fictional lab](claude-cue-lab.md) provides a bounded, explicitly invoked Claude Code runner with Opus 5.5. Cursor CLI with Composer remains an unimplemented alternative comparison. This is not a selected production runtime or an enabled background experiment; the lab's validation record separates offline checks from model trials.

Claude Code can use an API key from its environment instead of subscription login; its documented `--bare` mode does not use subscription credentials. Do not use that mode for this experiment or silently fall back to API billing. Keep this setup isolated from unrelated development credentials and settings. Use the vendor's normal sign-in flow and unmodified CLI. Do not extract session tokens or imitate private endpoints. A local CLI still sends selected context to a hosted model; it does not establish on-device inference. Begin with a bounded, user-started fictional replay, disable unnecessary tools and integrations, and verify local session storage and provider data settings before considering real conversations. Direct inference APIs and SDK-based product integration are deferred under the current no-API preference.

## Production remains a separate decision

Keep the semantic evaluator replaceable behind a narrow interface. A subscription experiment can test cue quality, but does not establish a dependable live service, acceptable tail latency, or frictionless onboarding. Do not require a coding subscription as the default distribution path without validating that choice with intended users. The local-first product plan remains the baseline; an optional hosted mode needs an explicit processing decision.

Anthropic's [product integration rules](https://code.claude.com/docs/en/legal-and-compliance) distinguish users signing into an unmodified Claude Code binary themselves from a developer routing everyone through a shared subscription or collecting their credentials. The documented binary integration has commercial terms and authentication conditions to review before distribution. Do not assume a personal lab setup grants a general-purpose hosted inference entitlement. Recheck Cursor's product integration terms before choosing it for distribution as well.

Measure conversational performance directly. Coding benchmarks and model size do not establish whether a model can judge when to stay quiet, and Opus is not automatically the right choice for a time-sensitive cue. A smaller model may earn the live role if it meets the same quality criteria sooner and uses less allowance.

## Rules baseline on the shared suite

The current phrase rules were run on the fictional cases the [Claude lab](claude-cue-lab.md) uses, through a live engine session (`rules_baseline_on_the_shared_fictional_suite` in `engine.rs`). "No cue raised" means the case starts with a visible cue, but the rules never raise one from the first line, so they cannot take part.

| Case                   | Expected | Rules (9 November 2026)                                                                             |
| ---------------------- | -------- | --------------------------------------------------------------------------------------------------- |
| missing-owner          | show     | show: "someone should" raises the owner question since the 9 November rule change                   |
| already-answered       | quiet    | resolved: the owner question is raised, then "I'll send it" withdraws it two seconds later          |
| visible-cue-resolved   | resolved | no cue raised                                                                                       |
| asked-but-unanswered   | quiet    | quiet: the owner question is raised and stays; the later lines change nothing                       |
| topic-moved-on         | withdraw | quiet: "Let's leave the cover choice for another meeting. Now, …" is not a recognized topic opening |
| uncertain-speaker      | quiet    | no cue raised                                                                                       |
| context-reminder       | show     | quiet: the rules have no context reminders                                                          |
| transcript-instruction | quiet    | quiet, and correctly ignores the embedded instruction                                               |
| context-corrected      | withdraw | quiet: "Actually, … staying where it is" has no explicit correction phrase                          |
| paraphrased-use        | resolved | resolved: the owner question is raised, then "I'll send it" withdraws it                            |
| repeated-trigger       | quiet    | quiet: the owner question is raised once; the repeat two seconds later is suppressed                |

The rules match the expected action in 5 of 11 cases; on the first eight they match 3. Later on 9 November the verbs a volunteer may use grew from "take" and five others to include "send", "do", "sort", "book", "check", and "look" (the suite's volunteers say "I'll send it"): paraphrased-use now matches, and already-answered becomes a question withdrawn two seconds after it appears rather than one that stays, still short of the expected quiet, because the rules cannot know an answer is coming. Before the owner rule gained "someone should" and "someone could" (9 November 2026, after the owner said "someone should look at the compost bins soon" in a live session and got only the timing question), they matched 2 of 11, both by doing nothing. The wider rule wins missing-owner, asked-but-unanswered, and repeated-trigger, and loses already-answered, because the rules have no answer phrase for "I'll send it": the trade is a question that is sometimes already answered against a question that was never raised. The open-question rule (9 November 2026) changes no row: the suite's open questions ("Who's taking care of sending it?", "Who's sending that?") open with "Who's", which the rule excludes as too common in call logistics. On those eight, the subscription-backed Claude lab matched 7, each run once ([lab record](claude-cue-lab.md#validation-record)). Its one disagreement, `missing-owner`, is a defensible judgment that a cue would duplicate what the speakers were already settling. The rules miss paraphrased triggers, context reminders, and topic changes said in other words. This is the comparison point for a semantic evaluator on the same inputs. Like the lab's own results, it is a smoke check on small examples, not evidence about real meetings.

### Outcome labels

Three labeled cases were added on 9 November 2026 to cover outcome signals the first eight lacked. They have not been run in the Claude lab, which would need a new explicit authorization:

- `context-corrected`: a speaker withdraws the premise behind a visible cue that asks for a new date ("Actually, the supplier review is staying where it is"). Expected: withdraw. The correction removes the cue's basis without answering it.
- `paraphrased-use`: the participant asks the visible cue's question in other words, and another speaker answers. Expected: resolved, with observed use "possible". Use and resolution are labeled separately; similar speech is a possible signal of use, not proof that the cue caused it or helped.
- `repeated-trigger`: a speaker restates the line that raised a visible cue. Expected: quiet, because a second cue would duplicate the one already shown. The rules never raise the first cue here, so this case does not exercise their two-minute repeat pause.

Across the suite, labels keep observed use and resolution apart; no case labels usefulness or involves dismissal. These are labels written by the developer, not outcomes observed in meetings.

## Smallest useful evaluation

1. Create a fixed fictional suite with useful opportunities, questions answered before display, paraphrased use, irrelevant matches, ambiguous speakers, topic changes, and context reminders that help without being spoken. Label source support, display/suppress decisions, and later outcomes separately.
2. Compare current rules, human-selected cues, and candidate semantic evaluators on the same inputs. Keep display policy fixed while comparing detection. The model under test must not be the sole judge of usefulness.
3. Measure false interruptions, missed opportunities, false suppression, source errors, outcome-label accuracy, and whether decisions arrive while still useful. Record cold/warm and tail latency, timeouts, device resources, and subscription allowance consumed. Do not mistake a successful offline judgment for a usable live cue.
4. Estimate evaluations per meeting from bounded input size, output/reasoning tokens, caching, and retries. Trigger on meaningful conversation changes and deduplicate work. Stop when the plan allowance is unavailable; compare sustainable session capacity with quality and latency before considering any separately billed service.
5. Select a runtime only after it meets predefined quality, timing, privacy, distribution, and cost criteria. Keep timeout, failure, and unsupported states quiet and understandable. Hosted selection does not silently replace the local-first product boundary.
