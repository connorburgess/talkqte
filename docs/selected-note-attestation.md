# Selected-note diagnostic attestation

This opt-in fictional lab diagnostic separates importing a note from approving it for processing. It is not a production integration, proof of model attention, or evidence of usefulness. Earlier runs that retained only import-selection screenshots cannot establish that a note was included in the processing grant.

The `selected-prior-attested-v1` context policy uses the existing selected-prior v2 input and exact system prompt. A private per-run authority binds an expected count of **one** for the selected diagnostic, or explicitly **zero** for its control. Native review and approval reject a different count. Nothing automatically selects, imports, or approves a note. The owner must inspect the actual source and check its processing-review checkbox.

After personal approval, native and the already-listening local broker exchange scope approval without opening a provider or worker. Native verifies that the grant remains current before confirming scope-ready. The shared prepared take includes this wait in its original absolute 180-second approval deadline. Only then may it open the provider, release the transcription token, report accepted approval, or start playback. The ordinary selected-v2 and legacy paths keep their existing behavior.

For each request, native compares its actual serialized note projection with the approved projection. The separately prepared JS attestation worker checks the actual `messages[0].content` projection against the same private run-keyed commitment immediately before SDK entry, then passes that frozen parameter object to the SDK without an intervening await. That worker is not included in this native source change or established by the public selected-context JS source; it requires its own review and explicitly paired package. Missing, changed, empty-selected, or observed-retired authority refuses before that call; there is no zero-note fallback.

The commitment uses HMAC-SHA256 with a fresh 32-byte run key. Its normative encoding is unsigned big-endian 32-bit length prefixes over: domain `talkqte.selected-note-attestation`, version `1`, run ID, canonical decimal native session, raw 32-byte grant nonce, and attested policy. The projection is a length-prefixed `selected-note-projection-v1` domain, a 32-bit count, then tuples sorted by unsigned UTF-8 ID bytes. Each tuple contains length-prefixed exact ID, provider, title, date, canonical opaque revision, freshness, and text. Nonce and digest travel as 64 lowercase hexadecimal characters; the nonce is decoded before hashing. Shared fixtures pin complete message bytes and digest. Unknown snapshot freshness and native revision semantics do not change.

Pending and ready grants are retired on source change, removal, revoke, Stop, or session replacement. Release and SDK boundaries check current authority. Retirement observed before a boundary refuses it; a concurrent retirement may race an already-entered SDK call. Such calls cannot be recalled: accounting and unknown outcomes remain, and late results are suppressed. There is no universal zero-cost cancellation guarantee.

Private bounded receipts contain only count, run/session/grant identity, commitment, and fixed stage labels. `dispatch_intent` records authorization before a call, **not** durable proof of invocation or remote receipt. A crash can leave gaps on either side of SDK entry; those gaps are unknown. Source text, title, dates, paths, provider source IDs, key, credentials, headers, and raw prompts are not diagnostic fields. Authority keys are local, outside the checkout, excluded from evidence exports, and passed to the SDK worker only through its private initialization pipe.

## Acceptance and remaining blocker

The native tests in this source exercise real review/approval, Link/socket scope handshake, Worker projection, source removal, revoke and ordinary Stop with fictional peers. Separately prepared JS tests exercise broker/provider/worker/SDK construction with a loopback fake stream, one-note and zero-note inputs, mutation/refusal and retirement, plus prepared-take wait/release boundaries. Those JS attestation and recording-checker changes are excluded from the public JS selected-context change and from this native change; their retained results are separate preparation evidence, not evidence that the public sources provide an integrated attested route.

Targeted offline Rust execution has since passed 47 four-feature checks and 13 default-feature selected-snapshot checks on a prospective composed tree. This does not replace full final-head Rust tests, Clippy, builds, hosted checks, independent review of the paired JS source, or compiled native-process end-to-end acceptance. No single integrated native/JS acceptance run is established by these separate tests.

A reviewed replacement native artifact, reviewed JS/runner composition, actual same-process source approval, and separately authorized future run remain necessary. The diagnostic does not alter model actions (`show`, `quiet`, `resolved`, `withdraw`), the 10-word/240-character glance rule, union citation validation, fresh-speech anchors, or default processors' note exclusions. A showcase is illustrative; opportunity labels and desired outcomes must never enter live model input.
