# Test selected application audio before integration

**Recommend a consent-scoped ScreenCaptureKit audio-output-only spike first**, preserving TalkQTE’s agreed macOS 14.0+ target. Test one fictional source alone before combining it with the microphone. Retain Core Audio process taps as a 14.2+ alternative if ScreenCaptureKit cannot meet the scope or lifecycle requirements. This is a planning decision, not approval to capture other applications, choose a production binding, or change the deployment minimum. Research checked **11 November 2026**; no capture, build, permission change or inference was performed. Native behavior and user outcomes remain unverified.

## The baseline is microphone-only; browser audio is application-wide

At [baseline `abbe365dd5db6502a5c4e9211ba531a7916dd54f`](https://github.com/connorburgess/talkqte/tree/abbe365dd5db6502a5c4e9211ba531a7916dd54f), TalkQTE’s `local-whisper` developer build implements local microphone capture/transcription and bounded handoff; this is not a general shipped capability, and other-app audio is absent. Rust owns capture and lifecycle, with native differences behind adapters. Claude remains lab-only. The owner-agreed target is Apple silicon, macOS 14+, English, Meet in Chrome followed by Zoom, initially built-in audio and wired headphones. These are intended configurations, not established support claims. ([Architecture](https://github.com/connorburgess/talkqte/blob/abbe365dd5db6502a5c4e9211ba531a7916dd54f/docs/architecture.md), [budgets](https://github.com/connorburgess/talkqte/blob/abbe365dd5db6502a5c4e9211ba531a7916dd54f/docs/budgets.md); baseline reviewed 2026-11-11.)

Apple documents **application-level audio filtering even when video selects one window**: other windows of that application can contribute audio. Therefore the consent must say application audio; neither candidate establishes Meet-tab isolation. ScreenCaptureKit’s native picker arrived in macOS 14, but SDK inspection found filter `includedApplications`/`includedWindows`/`includedDisplays` getters require 15.2. Truthfully identifying the selected application on 14.0 is an explicit spike gate; modern getter-based labeling cannot be assumed. ([Apple WWDC22, 2022](https://developer.apple.com/videos/play/wwdc2022/10155/), [WWDC23, 2023](https://developer.apple.com/videos/play/wwdc2023/10136/), [SCContentFilter, undated](https://developer.apple.com/documentation/screencapturekit/sccontentfilter); checked 2026-11-11.)

## Compare two APIs without silently changing the target

| Candidate               | Documented boundary and tradeoff                                                                                                                                                                    | Decision to test                                                                                                                                                |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ScreenCaptureKit        | Audio outputs/configuration are available from 13.0; native picker from 14.0. Audio scope is the application. Screen-capture permission behavior needs actual OS testing.                           | Register only `.audio`; exclude TalkQTE output; omit screen handlers, previews, screenshots and recording APIs. Preserve the existing separate microphone path. |
| Core Audio process taps | Tap creation requires **14.2**, although `CATapDescription` itself is marked 12.0. Apple’s sample uses a tap and aggregate input with `NSAudioCaptureUsageDescription` and system-audio permission. | If needed, compare a private, unmuted, explicitly included process set. Verify helper-process mapping; never fall back to global exclusion/all-app capture.     |

These availability statements come from Apple documentation and read-only inspection of the macOS 26.5 SDK headers (`SCStream.h`, `SCContentSharingPicker.h`, `AudioHardwareTapping.h` and `CATapDescription.h`), not runtime tests. Core Audio’s bundle-ID/process-restoration conveniences require **26.0** and cannot solve 14.x identification. An aggregate input is a native resource to destroy, not a requirement to install a virtual driver. ([Apple Core Audio sample, undated](https://developer.apple.com/documentation/CoreAudio/capturing-system-audio-with-core-audio-taps), [tap creation](<https://developer.apple.com/documentation/coreaudio/audiohardwarecreateprocesstap(_:_:)>), [bundleIDs](https://developer.apple.com/documentation/coreaudio/catapdescription/bundleids), [ScreenCaptureKit configuration](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration); checked 2026-11-11.)

Registering only audio avoids a TalkQTE video-frame handler; it **does not prove zero internal OS video processing**. Compare the necessary lifecycle slice of `screencapturekit` against `objc2-screen-capture-kit`; a small native bridge is a fallback if required APIs are missing. Inspect and pin licensing, availability, callback ownership and asynchronous teardown before a later spike dependency change. Select a production binding only after native acceptance. The maintainer’s example attaches both audio and video and uses broad filtering, so it is not TalkQTE’s consent policy. ([Maintainer example](https://github.com/doom-fish/screencapturekit-rs/blob/main/examples/03_audio_capture.rs), [objc2 binding 0.3.2](https://docs.rs/objc2-screen-capture-kit/0.3.2/objc2_screen_capture_kit/); checked 2026-11-11.)

## A source-only experiment earns the next integration step

Offline planning can define selection, cancellation generations, bounded queues and synthetic fixtures now. It does not require capture permission and does not establish native correctness. Keep other-app audio capture disabled pending new, explicit authorization for the bounded experiment. Explicit scope disclosure must precede any enumeration or OS request that may itself trigger access. First use one synthetic application with a distinctive audio marker while an unrelated application emits another. Verify selected inclusion, unrelated exclusion, truthful application scope, permission handling and actual release on 14.0 and the current tested OS. Stop if the candidate fails; do not widen scope automatically.

The [offline application-audio boundary](application-audio-boundary.md) now implements exact review ownership, one start attempt, cancellation and reservation through returned-resource cleanup. Nine fictional tests exercise these controls without OS access. The bounded synthetic handoff also preserves operation identity and frame gaps with eight additional tests. Native clock mapping, filtering, startup deadlines, rendered consent and actual release remain separate implementation/acceptance steps; the native capture permission gate does not block their independent offline preparation.

Only then add the existing microphone, preserving source identity and mapping native timestamps into a shared session clock before any deliberate mixing. Use fictional Meet/Chrome and Zoom scenarios, wired headphones then speakers, to expose acoustic duplicates and timing drift. Source identity is not speaker identity. No provider integration, recording, upload or inference is needed for the capture-only stage.

| Proposed acceptance gate | Smallest useful evidence; all remain open                                                                                                                                                                                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Consent and UI/UX        | Reviewed policy names the application-wide scope; native flow truthfully identifies it. Keyboard selection, Cancel and Stop work without losing focus. Cancel captures nothing; denial/error explains recovery and preserves independent microphone choice. This document reviews policy, not a rendered or tested flow. |
| Privacy and scope        | Selected marker only, with the browser’s broader app-audio scope explicitly demonstrated. Zero delivered video buffers; no media in webviews, files, temporary storage, logs or network. No global capture or virtual driver.                                                                                            |
| Lifecycle                | Late start completion cannot reactivate cancelled capture. Measure actual source release, not command completion; propose ≤1 second, extending the microphone target. Denial, revocation, app/helper exit, device change and sleep/wake never broaden or silently restart capture.                                       |
| Audio contract           | Distinct source IDs, measured clock drift/discontinuities and correct channel/resampling handling. Bounded preallocated callbacks perform no inference, blocking work, disk/network or logging. Slow-consumer tests expose counted drops/time gaps. Mic pickup does not create duplicate remote transcript lines.        |
| Performance              | Measure capture alone, then combined/full pipeline against existing budgets: zero dropped chunks/60 minutes, backlog ≤2, app memory ≤600 MB, transcript p95 ≤5 seconds, average CPU ≤15% of one core and battery ≤8%/hour on the target M1/8 GB. These remain targets, not results.                                      |

## Authorization and hardware are the next dependencies

The next dependency is explicit authorization for synthetic other-app capture, adequate build/storage headroom, and suitable macOS 14.x hardware—not a provider adapter. Minimum-device performance and native permission/packaging tests remain separate gates. Defer Bluetooth, automatic source detection/restart, browser-tab extensions and dual production adapters. If evidence forces 14.2+, the owner must choose among a higher feature floor, microphone-only operation on 14.0/14.1, or a second adapter. Neither successful compilation nor this plan justifies support or improved-participation claims.
