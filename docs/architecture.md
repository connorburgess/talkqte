# Desktop stack decision

Status: accepted for the initial implementation, 2026-11-08.

## Decision

Use Rust for the application core, Tauri 2 for the desktop shell, and React with TypeScript and CSS for the interface. Ship macOS first. Use cloud streaming (Deepgram) for speech recognition, behind the `StreamingTranscriber` boundary, sending audio only after per-session approval; there is no on-device recognizer (removed on 16 November 2026). Keep the native capture adapter separate from transcription and presentation.

## Why this stack

| Option               | Strength for TalkQTE                                               | Main trade-off                                                                                       |
| -------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Rust + Tauri + React | Native core, flexible interface, a path to other desktop platforms | Native capture and overlay behavior still require platform-specific work; system webviews differ     |
| Swift + SwiftUI      | Direct access to macOS audio, permissions, and window APIs         | A second desktop UI and platform layer would be needed for Windows                                   |
| Electron + React     | Mature web-based desktop tooling and predictable bundled Chromium  | A bundled browser/runtime and a JavaScript main process; native audio integration is still necessary |
| Rust-only UI         | One primary language and close native integration                  | More UI/toolkit work for this interface and less reuse of web styling experience                     |

Tauri does not turn native audio capture into a solved problem. Its system webview avoids bundling Chromium, but actual memory, package size, responsiveness, and battery use must be measured during a live session. Transcription streams audio over the network instead of running inference on the device; its on-device cost has not been measured.

## Explicit question boundary

`meeting_qa.rs` owns bounded frozen transcript tickets, request budgets and validated source IDs; the engine owns each record and withdraws it on Stop/revoke/replacement. `meeting_qa_commands.rs` dispatches outside the engine lock over the existing fixed provider transports, then accepts the response and any auth-rejection side effect under that lock only for the still-current ticket. The companion can only request opening/focusing the main transcript/Ask panel; its capability cannot prepare, send, cancel or read questions/history. React never supplies a session identity or request destination. See [live questions](live-questions.md) for separate explicit Send permission, limits, retention and acceptance gaps.

## Boundaries

### Current prototype

`src-tauri/src/engine.rs` owns the session clock, applies limited phrase rules to the lines a live session supplies, and owns the question lifecycle and in-memory notebook. With no session it is idle: nothing is scripted and nothing plays. The engine can still replay scripted lines on its clock, which only its own tests use; their fictional scenario is the fixture `src-tauri/src/engine/fictional_scenario.json`, compiled into test builds only. The in-app demo that played that script was removed on 14 November 2026. A native timer and commands synchronize elapsed time under a mutex. Native visibility updates do not call blocking window getters while holding that mutex.

The main webview receives session snapshots. The floating webview receives only the current question and display state, and has a smaller Tauri command capability. Revisions keep late snapshots from replacing newer UI state. React sends note edits through an ordered command queue; export preparation waits for those edits.

`src-tauri/src/companion.rs` owns the floating window's compact, question, and context states. It defaults to the bottom-right of the active display's work area (following the frontmost application window or pointer, falling back to the notebook display and primary display), with optional top-center, top-left, and top-right presets. Rust-owned appearance settings travel with both snapshots. Native window queries run on the main thread after releasing the engine lock. Placement is checked on notebook moves and once per second so display and Dock changes can be handled without querying window state in the engine's critical section. Only changed layouts are applied. The window is configured not to take focus; keyboard question controls remain in the notebook. Full-screen apps, Spaces, native assistive access, and screen sharing still require separate verification. Automatic meeting detection is not implemented.

Glance view initially hides the evidence excerpt. The ID-validated `inspect_cue` command updates shared disclosure state and marks the current question held in Rust. Playback and transcript updates continue, but expiry cannot remove a held question and later suggestions do not replace it. Collapsing context retains the hold. The original deadline still supplies an earlier-question label; it is not semantic resolution. Dismiss remains available in the UI whenever that same question exists. Stopping the session clears it, held or not. Untouched questions retain the existing expiry/cooldown policy. Skipped questions are never replayed from a backlog. See [design and evidence](glance-mode.md).

On macOS, `src-tauri/src/companion_macos.rs` selects a native titled frame with full-size content before the window is created. AppKit supplies its rounded outer corners while the webview remains opaque. Setup hides the title and standard window buttons before the companion first appears, using public AppKit APIs on the main thread. Setup and `show` also configure AppKit to float the companion at `NSStatusWindowLevel` without hiding on deactivation, show it on every Space and over other apps' full-screen windows (`canJoinAllSpaces`, `fullScreenAuxiliary`), keep it out of the Command-Grave Accent window cycle, and order it front with `orderFrontRegardless` without stealing focus; it still appears in Mission Control. It is an ordinary window that cannot take focus (Tauri's `focusable: false`), not an AppKit non-activating panel: showing it is meant not to take focus, though a click on it may still activate TalkQTE, and whether it does is not yet checked. Each move or resize of the companion is a single AppKit frame change (`setFrame:display:`), so no part-moved, part-resized frame exists in between; if the primary display cannot be read, it falls back to Tauri's move, resize and move. This keeps platform window details out of the lifecycle and rendering code; other platforms retain the borderless configuration. Compact and expanded native windows have been visually checked on macOS; presence on every Space and over full-screen apps, cross-app keyboard focus and the single frame change are not yet checked on hardware. The [native validation record](native-validation.md) separates observed notebook behavior, geometry tests, and pending companion checks.

`src-tauri/src/settings.rs` owns the only file the app writes on its own: `settings.json` in the app's Application Support directory, preferences only, format version 1, replaced atomically and readable by the owner only. It is read once in setup and applied, whole, before the first snapshot; development launch settings apply over it and are never written to it, and a lab run neither reads nor writes it. Each setting command records its own change after it takes effect (`settings_commands.rs`); the companion can change only what it could already change (hiding itself). Keys stay in the Keychain and nothing from a meeting is written ([privacy](../PRIVACY.md)).

On macOS, `src-tauri/src/menu_bar.rs` owns the menu bar item (a Tauri status item with a template image drawn from the mark) and what closing the notebook does: it quits unless the person turned on Keep running in the menu bar, and then hides the notebook and leaves the Dock (accessory activation policy) until the notebook is opened again. The menu's model (`items`) is pure and tested; its choices only open the notebook, emit the notebook's ordinary start, stop a running session, toggle the call-starting setting or quit. `src-tauri/src/login_item.rs` registers the app through `SMAppService.mainAppService` behind a small backend trait, with a fake for tests and none in a lab run; the state shown is always read back from the system.

Export preparation stores a Markdown snapshot in Rust. The subsequent native save dialog writes that exact snapshot, not a new version assembled after the user reviews it. The frontend cannot supply an arbitrary filesystem destination to the export command. `src-tauri/src/meeting_history.rs` and `meeting_history_commands.rs` keep ended live sessions only when the person chooses **Keep meeting**, in owner-only versioned JSON files under `meetings/`, and prepare the same preview-before-save Markdown snapshot when exporting a kept meeting from **Meetings**; lab launches neither read nor write them. `HistorySource` also exposes kept meetings' kept meeting notes and user notes (never transcripts) through the `context.rs` `NoteSource` contract (`Provider::History`).

The browser preview uses `src/lib/preview.ts`, a development-only simulation. Its UI tests complement the Rust engine tests; they do not test Rust IPC, native dialogs, or native windows. There is currently no full meeting-audio pipeline or database. Application-audio capture exists only in a `native-audio-spike` development build on macOS, through one unvalidated command that has not been run on a device ([below](#next-native-spike-and-acceptance-criteria)); an ordinary build has no application-audio entry point. The note-file and Granola adapters are described below.

The engine exposes one transcript input boundary for transcription feeds: `Engine::ingest(session, segment)`. A worker records `Engine::session()` when it starts and attaches that value to each segment. Ending a session or starting another issues a new session, so late work for an earlier session is rejected. Input is accepted only while the session is running, at or before the current elapsed time, in order, with a unique short ID, a speaker label up to 80 characters, and 1–1,000 characters of text. Rejected input leaves state unchanged. Times are on the engine's session clock, which advances on native ticks and stops while paused. A worker must convert audio timestamps to that clock, or its segments will be rejected as coming from the future. IDs must be unique within the session. Accepted segments go through the engine's cue, answer, and stale-cue rules. The in-memory transcript keeps the latest 50,000 segments; duplicate IDs are detected only within those. The Markdown export holds the person's notes only and never a transcript line; export is refused while a live session runs, and after it ends only the notes are exported. `src-tauri/src/transcription.rs` defines the 16 kHz mono audio chunk shared by capture paths and exposes the cloud modules. `transcription/cloud.rs` supplies `CloudFeed` and the `StreamingTranscriber` contract. The feed binds one engine session and capture-clock mapping, discards audio before processing approval, and passes only validated final results to its sink; microphone and application-audio sinks retain their session/source guards. A full stream queue drops audio rather than blocking capture. Revocation retires the stream, and reconnect attempts remain under the same approval and launch budget, with no replay of lost audio or fallback recognizer. `Engine::live()` creates a session with no scripted lines. The former `Transcriber` worker, `LocalWhisper`, `local-whisper` feature and model-file setup were removed on 16 November 2026; the [local transcription check](local-transcription.md) preserves their historical design and measurements, not current setup. See [current cloud behavior and limits](cloud-transcription.md).

`src-tauri/src/audio_tap.rs` is the bridge between microphone capture and the transcription worker. Its callback side downmixes interleaved samples to mono and pushes them into a fixed four-second lock-free ring (`rtrb`) without allocating, locking, or blocking; when the ring is full, samples are dropped and counted. A chunker on another thread drains the ring, resamples to 16 kHz (averaging when downsampling, which gives only minimal anti-aliasing, and linear interpolation when upsampling), and cuts chunks timed on the session clock: fixed-length by default, or, with `cut_at_pauses`, at the first pause after a minimum length and never longer than the set length. Live sessions use fixed 100 ms chunks for the cloud stream. With `cut_at_pauses`, a full-length chunk of near-total silence is skipped and counted; later chunk times are unchanged. Dropped audio leaves a gap so later chunks keep their times, a frame split across callbacks is kept, and stopping returns every remaining chunk once capture has stopped. Chunk times come from counting samples, so device clock drift and pausing the session can still move them off the engine's clock. Tests cover 8–48 kHz input, downmixing, split frames, overruns and the gap they leave, clipping, the remaining chunks on stop, and chunk timing over ten minutes at 48 kHz. An earlier check with the former on-device recognizer fed the fictional meeting at 16 and 48 kHz through the tap and raised the expected question, with no overruns. The live session connects the microphone to the tap.

`src-tauri/src/context.rs` defines the source-aware contract for prior notes a user selects from a note-taker or a file. It covers validated items with provider, date, excerpt, and revision; separate import, live-input, and writeback capabilities; and connection status. Fetching, with bounded retries and cancellation, runs outside the in-memory store, so no lock is held during network work. The store accepts only selected notes, deduplicates by revision, and deletes copies only on an explicit removal, which is separate from disconnecting. Imported notes are kept apart from live meeting evidence. The first adapter is `src-tauri/src/notes_file.rs`: a JSON notes file, or one Markdown or plain-text note, that the user picks through the native dialog (at most 1 MB, and 200 notes for JSON) is parsed into context items; a Markdown or plain-text note whose file gives no date is imported only with a date the person enters in the chooser, which never replaces a date from the file ([file rules](note-file-formats.md)). The items are listed for selection, and only the ticked notes are merged into the store held in the runtime; `context:changed` carries the items to the main window, which can remove them singly or all at once. The file adapter has no authentication or network access; the ordinary phrase-rule engine uses selected items for the title-word context reminder. Separate development evaluator paths may use exact selected notes only after their own processing review and grant; importing notes grants no processing permission ([selected-context scope](selected-context-lab-opt-in.md)). See [integration readiness](product-readiness.md#integration-readiness).

The optional [Claude cue lab](claude-cue-lab.md) is a separate Node development script, not an application inference worker. It sends one bundled fictional case through the official subscription-authenticated CLI, checks the returned decision and source IDs, and prints a report. It cannot mutate Rust cue state, receive captured audio, or supply live app prompts. That single-case script is distinct from the development app connections described below: those use Rust-owned workers, validated source/version boundaries, resource budgets, cancellation and explicit session processing approval.

### Microphone activity on macOS

`src-tauri/src/microphone.rs` owns a separate, default-off microphone monitor. Only the main window can invoke `start_microphone`; the main and companion windows can invoke `microphone_snapshot` and `stop_microphone`. During a live session, `stop_microphone` stops the whole session (see below). The `microphone:changed` event contains only a revision, status (`off`, `starting`, `listening`, `stopping`, or `error`), a `canStart` flag, coarse activity (`quiet` or `active`), an optional public error message, and the opened input's display name (`deviceName`, or null). `canStart` is true only when monitoring is off or a failed stream has finished cleanup; cleanup completion emits a newer revision so the UI can enable retry. Consumers must ignore older revisions. No samples, device identifiers, or precise levels are sent to webviews. The adapter caches the same opened device's name after explicit start and permission; the controller strips control/direction-override characters and bounds it to 120 characters. It is local display metadata, never persisted, logged, exported or supplied to the transcript/cue evaluator. Name lookup failure does not stop capture. Starting/listening snapshots retain the label, Stop retains it as releasing until teardown, and Off/error clears it. A cancelled late start cannot publish its label. See the [input visibility checkpoint](microphone-input.md).

The native adapter checks AVFoundation microphone authorization and requests permission only after the explicit start command. Once authorized, a worker creates a CPAL input stream for the current default microphone in its native format. Status remains `starting` until samples arrive. Cancelling a pending start invalidates its generation, so a late permission result cannot restart monitoring. Microphone commands await controller work on blocking workers; native window/timer reads skip busy state instead of waiting behind device startup. App exit schedules cleanup without blocking the event loop. Once stop is accepted, `stopping` remains visible until teardown completes, then an event reports `off`. New starts are rejected during teardown, including cleanup after an error; errors require an explicit retry. There is no automatic device switching or automatic restart.

The audio callback inspects at most 4,096 samples per buffer and writes only atomic activity, buffer-count, and failure summaries. It does not allocate an audio buffer, lock application state, emit events, log, write files, or retain samples. A native poll reads those summaries every 200 ms, holds the activity indicator briefly to avoid flicker, and requests capture cleanup on a stream error or after three seconds without callbacks. Native stream destruction runs on a blocking worker after publishing the error, so a slow device cannot hold up the demo timer or companion updates. This level threshold detects signal activity, not speech, speakers, or meeting participation.

Microphone monitoring is independent of a session. It does not capture system output, other apps' audio, or both sides of a call. It does not transcribe, record, retain audio, use a model, or send audio over the network. The browser preview does not request microphone permission. Synthetic tests cover signal, lifecycle, and deliberately blocked stream teardown behavior without opening a real device; permission prompts, device changes, and real-device operation still need opt-in native verification.

The notebook exposes explicit Start microphone and Stop microphone controls separately from a live session. The compact companion remains available during microphone starting, activity, stopping, and errors even when no session is running. Hide only hides the window; it does not stop monitoring. The microphone check raises no cues; a live session (below) is labelled live. Frontend tests use a test-only mocked IPC entry point; the browser preview itself never simulates microphone activity.

### Live session

The runtime owns one bounded `processing_reviews::Reviews` store for processing commands. Its opaque ID refers to a single-use Rust engine token, with an additional digest of available notes; reconciliation after control/source changes discards stale reviews without widening a valid grant. `Engine::begin_live_stop` closes processing before transcript drain, and `finish_live_stop(session)` ignores old cleanup completions. The stopping flag does not confirm microphone release. These gates have [fictional native review acceptance](native-processing-reviews.md); the [processing status contract](native-processing-status.md) publishes metadata to the main window. Main-only [processing commands](native-processing-commands.md) bind review preparation, Disable and Pause/Resume to the originating session/scope, with opaque-ID-only approval and cancellation. [Capture Stop](scoped-capture-stop.md) instead uses stable live-operation ownership and an exact microphone generation, checked again by the adapter outside Runtime. Note changes do not block Stop. The [notebook integration](notebook-processing-controls.md) shares native status for capture and permission controls; provider activation and real-device acceptance remain separate.

`src-tauri/src/live_control.rs` reserves a single startup ticket before the start step. Stop cancels it without waiting for that step; its reservation remains until the blocking step exits, and a cancelled result cannot install an engine. Microphone startup registers its generation with that session before requesting permission, allowing Stop to retire a pending start. End-session and microphone-loss cleanup use the same early processing revocation before queued transcript drain. See [headless startup acceptance and remaining UI/native checks](live-start-cancellation.md).

`src-tauri/src/live.rs` runs a live session without depending on Tauri. In a build with a cue connection and a usable Deepgram credential (the stored key, or in a debug `cloud-transcription` launch the token-file settings), the main window's `start_live_session` command takes the cloud stream's opener (nothing is opened yet), installs `live_engine()` (keeping display settings and notes), and starts the microphone with a tap of 100 ms chunks. That engine uses phrase rules unless a separately selected development evaluator is registered. Any other build or launch refuses the start with a plain reason. The capture callback then also pushes samples into the [audio tap](#current-prototype) without allocating, locking, or blocking. Once capture really starts, a one-shot callback receives the tap's chunker and starts a `LiveSession` only if the engine session is still current; otherwise it releases the microphone. Chunk times start at the engine's elapsed time when capture began. A runner thread drains the tap every 250 ms into a `CloudFeed`, which discards audio until the session's processing review is approved, then opens the stream and sends it; only finals go to `Engine::ingest` under the engine lock and are published to both windows. Turning the review off, the minute cap, or a terminal stream failure ends the session with a fixed reason; Stop sends the last audio and waits up to 10 seconds for the last results ([cloud transcription](cloud-transcription.md)).

The runtime holds the live session's engine session ID, the microphone start's generation, and the runner. `stop_live_session`, also allowed for the companion, takes these out under the lock, releases that microphone start only (a later capture is never stopped by a stale request), then outside the lock hands the remaining audio to the worker and waits up to 10 seconds before ending the engine session, only if it is still that session. A second Stop finds nothing to stop. `stop_microphone` during a live session does the same. The native timer ends a live session whose microphone start is no longer starting or listening, for example after a refused permission or a device failure; it reads the microphone state without waiting. A replacement engine continues session numbering from the one it replaces, so late lines from a live session are refused by the next session. The live clock and transcription cannot be paused. The separately validated `set_live_cues_paused` command, available in both windows, clears the current cue (including a held one) and suppresses new cues while transcript ingestion continues. Resume records the current elapsed time; delayed lines at or before that boundary remain in the transcript but cannot raise cues. Both snapshots expose `cuesPaused`, and Stop/new-session resets it. `export_preview` still refuses live sessions, so their transcripts are never written out. See [cue pause acceptance](live-cue-pause.md). `live_status` reports availability, a fixed unavailability reason and the selected transcription provider. Availability checks the development feature, launch selection, settings and token-file metadata; it neither loads a speech model nor confirms provider/account access. Model download, progress and removal commands were retired with on-device transcription. The cue snapshot carries a `live` flag so the companion can label the session. Tests run the session with synthetic audio and scripted streams; cloud provider/account, real-device timing and dependable Stop/recovery acceptance remain separate.

The macOS bundle requires macOS 14.0 or later and includes `NSMicrophoneUsageDescription`, which covers both the activity check and live transcription, and the generated third-party notices at `Contents/Resources/THIRD-PARTY-NOTICES.txt` ([release path](release-path.md#third-party-notices)); the audio-input entitlement is configured in `Entitlements.plist` and is embedded when signing. For a local bundle check, use `APPLE_SIGNING_IDENTITY=- npm run tauri -- build --debug --bundles app` to ad-hoc sign with the configured entitlement. An unsigned development build is not evidence that entitlements were applied. Inspect the built bundle and signature without invoking microphone start automatically. Ad-hoc signing is not Developer ID signing or notarization.

### Session clock precision

The native runtime retains sub-millisecond active time between clock updates,
including across a scripted test scenario's pause and resume. Ready, paused and ended time does not advance
playback; replay or engine replacement clears the previous session's remainder.
Pausing live cues still leaves the session clock running. Deterministic runtime
tests cover frequent fractional updates, cue expiry, pause, replay and replacement;
all four regressions fail with the previous per-update truncation. This prevents
cumulative rounding loss, but does not establish native audio clock correspondence,
device drift, callback timing or live-meeting usefulness. Those remain separate
acceptance gates before connecting application audio.

### Planned meeting pipeline

```text
Native capture adapters
        |
bounded audio buffers
        |
Cloud stream (after approval) -> transcript segments -> cue evaluator -> cue lifecycle
                         |                                  |
                  private storage                    Tauri events
                                                            |
                                                 dashboard + overlay
```

- Capture adapters own device selection, permissions, stream lifecycle, timestamps, and platform differences.
- The transcription stream owns audio framing, network I/O and cancellation on its own thread. Do not perform this work in audio callbacks or on the UI thread.
- Rust owns prompt expiry, cooldowns, persistence, retention, and session boundaries.
- React owns rendering, keyboard interactions, and presentation. It accesses native behavior only through narrowly scoped, validated commands.
- Every build can stream a live session's audio to Deepgram, with the person's stored key or a development token file, through the `StreamingTranscriber` boundary in `transcription/cloud.rs`, over a WebSocket client (`tungstenite` with `rustls`). The capture paths feed it the same 16 kHz mono audio; it sends nothing before the session's processing review is approved, and only finals become segments ([cloud transcription](cloud-transcription.md)).
- AI cue reasoning has a provider-independent worker and validated contract in `cue_evaluator.rs`, tested with fictional evaluators. It permits one outstanding request, checks source references, and rejects cancelled, expired, or changed-context results. Ordinary builds retain phrase rules; `live_engine()` can register a development CLI or explicitly selected lab evaluator under its feature/launch gates, with processing disabled until session approval. Rust retains lifecycle and permission control. These hooks do not establish a supported production runtime or useful semantic cues. See the [worker contract and remaining integration](cue-evaluator.md) and [cue intelligence plan](cue-intelligence.md).

## Future integration boundary

Granola and other note-taking apps are future sources of selected meeting context and destinations for user-approved exports. Keep provider-specific authentication and data mapping in separate adapters, using supported file exports or documented APIs. Verify each provider's access, plan, and data availability before committing to an integration.

Imported notes should use the planned Rust-owned selection, persistence, retention, and prompt-context boundaries. Preserve source identity and distinguish imported content from user edits so repeated imports can be reconciled explicitly. External content is meeting data, not permission to execute commands or send data elsewhere.

Start with one-way import/export. Live transcript access and two-way synchronization require separate capability checks and conflict/deletion rules. Connections remain optional; an unavailable provider must not block local capture or notes. `src-tauri/src/granola.rs` (9 November 2026) is the first adapter: the person signs in to Granola in the browser (OAuth 2.0 with PKCE and dynamic client registration, a loopback return), the app opens an MCP session and uses `list_meetings`, `get_meetings`, and the fixed `query_granola_meetings` question only when requested; tokens stay in process memory, and the notes a person ticks go through the same store as a file's. The notebook offers it; account checks have confirmed sign-in and listing. The observed tagged detail fields (`private_notes` and `summary`) are mapped and tested through a fictional MCP server and the context store; the owner confirmed basic native import and removal on 11 November. Real-account refresh, recovery and data-flow checks remain. Unknown nested content formats fail explicitly. Missing selected IDs fail the request before any notes are merged, allowing a retry with fewer notes. `context_import.rs` retains the pending source after a failed fetch, prevents concurrent attempts from the same chooser, and invalidates late results when the chooser is cancelled, replaced, or disconnected. Fetching and retry waits run outside the runtime lock; cancellation stops further retries and discards the response but does not abort an already-sent HTTP request.

`src-tauri/src/context_refresh.rs` holds one explicit update check of the Granola notes already selected, reached through the notebook-only `check_granola_updates` and `stop_granola_update_check` commands; it needs a provider-supported workspace identity, which the Granola adapter does not report, so the signed-in connection neither offers nor runs it ([scope and rules](selected-note-refresh-plan.md#first-slice-one-explicit-check-simulated-provider-only)). Its `eligible` list is what the engine receives through `set_prior_notes`, by way of the window-free runtime steps in `context_runtime.rs`: a copy a check could not confirm reminds with a warning, and one the provider reported as withdrawn is left out ([policy](selected-note-refresh-plan.md#reminders-from-copies-a-check-could-not-confirm)).

### Retiring Granola sessions and removing context

`granola::Shared` carries a retirement flag across every clone. Disconnect sets it without waiting for the connection mutex, drops idle credentials, and prevents queued calls from using the old connection. A call already holding the connection discards its result and drops credentials when it returns; an HTTP request already sent is not aborted. Listing and suggestion commands also compare the originating shared connection with the current one before accepting a result, so reconnecting cannot make a retired result current. Disconnect cancels pending sign-in and the Granola chooser, while existing imported copies remain in the context store until explicit removal.

Synchronizing the context store passes complete `ContextItem` values to the engine, preserving provider identity, source ID, revision, date, title, and excerpt across engine replacement. A newer revision, changed metadata/text, or removal clears a reminder quoting the previous item even when held open; the snapshot revision advances and both windows receive the new state. The reminder is not rewritten or re-armed for this session. Unchanged and older imports, updates to another provider's note with the same source ID, unrelated transcript cues, and manual notes remain unchanged. See the [headless acceptance record](note-revision-cues.md). The generated Markdown contains only the person's manual notes, with no transcript text, imported excerpts or cue payloads; export remains unavailable while a live session runs. Optional provider diagnostics use a bounded, allowlisted structural projection; tool schemas and arbitrary JSON keys are not presumed public.

## Next native spike and acceptance criteria

Before that spike, `application_audio.rs` supplies a development-only single-source
review/start/cancel boundary. It binds an immutable application selection to a
one-use review and scoped Stop, reserving the operation until its pending start
and returned stream have been released. Adapter work and destruction occur
outside the state lock. [Synthetic acceptance](application-audio-boundary.md)
establishes ownership only. Its `handoff` submodule carries bounded synthetic
audio with exact operation identity, immutable format, absolute frame positions
and explicit gaps. Its `timing` submodule binds one reader to a session and an
explicit frame-zero origin, with checked absolute-frame conversion and
frame-level discontinuities. Returned work still requires source/session guards.
Native filtering, clock origin/drift, deadlines and actual source release remain
unimplemented or unverified. The optional [native owner](native-audio-owner.md)
now has a dedicated-worker loop and a sendable control handle. Native objects stay
on their constructing thread through cleanup; host-handle loss requests Stop,
and abandonment remains distinct from release. In a default build no app command enables this path; a `native-audio-spike` development build has [one unvalidated command](native-application-audio-host.md) that does. The current source loop accepts source/session-bound 16 kHz mono native blocks and passes them to the cloud feed; the former three-second recognizer `chunks` submodule was retired with local transcription. Its historical synthetic chunking checks do not establish current cloud or native-device acceptance. The microphone path remains separate.

`src-tauri/src/live_source.rs`, compiled in every build, lets the runtime hold at
most one application-audio source attached to the running live session. Stopping
or replacing that session cancels the attached source under the runtime lock,
and a line from a source that is not attached is refused. In an ordinary build
nothing ever attaches a source, so this changes no app behavior.
`src-tauri/src/native_source.rs` is the development-only host loop that would
attach one: it is compiled only on macOS with the `native-audio-spike` feature,
and moves native blocks of its own operation and session to a cloud
transcription stream, whose finals go to that source sink. In a default build no command, picker, enumeration or permission
request calls it, so nothing in the app starts application audio. A
`native-audio-spike` development build adds a
[host with one command](native-application-audio-host.md) that can list
applications and start one; it has not been run against a device. See [ownership, sink and tests](native-audio-owner.md#live-session-ownership-of-the-source--13-november-2026).

1. Capture both sides of a synthetic call with headphones, with clear microphone/system permissions.
2. Stop and pause promptly; test device disconnect and permission denial.
3. Measure transcription latency and resource use on the target Mac while the meeting app runs.

### Evaluator lifecycle development boundary

The [bounded evaluator](cue-evaluator.md) has a source-aware engine bridge in `engine/evaluation.rs`. `Engine::live_with_evaluator` registers an explicitly supplied worker and immutable processor configuration, initially disabled. A Rust-owned session review/grant separately approves new or recent speech and exact prior notes, preserving provider/date/title/revision. Changed approved notes, revocation and session replacement cancel work and clear copied cue evidence; imports never widen permission. The [permission acceptance record](cue-evaluator.md#session-processing-permission) describes the boundary and remaining UI/adapter gates. Ordinary builds construct the phrase-rule engine; optional development connections use `live_engine()` and retain the same session review/grant boundary. The alternative path ingests the same validated transcript, applies the same controls and clock, and polls under the engine lock. New eligible speech requests evaluation; one boolean notification coalesces speech received while the worker is occupied, and a normal clock poll dispatches current context once it is free. Controls discard waiting work. The engine uses a separate eligibility revision from snapshot time, cancels obsolete work, and rejects late results before mutating the visible cue. Transcript and provider-note IDs occupy separate namespaces. State-changing proposals require a fresh cited transcript anchor, while selected notes remain prior context. Cue and resolution snapshots include only the cited sources, rendered individually with source labels; refreshing/removing a cited note invalidates delayed results and clears held evidence. The boundary itself grants no provider or capture activation. Development connection selection and user-facing permission controls are separate gates; their source implementation does not establish paired runtime, provider, device or usefulness acceptance.

## Remote speaker naming

`Segment::speaker_id` carries the optional provider diarization index through the cloud feed. Rust assigns numbered remote display labels, falling back to Them, and clears remote IDs from microphone lines. Main-window-only rename commands validate names and update the per-meeting map; React renders the shared inline `SpeakerChip`. Ended meetings persist optional IDs and names in backward-compatible v1 fields, and transcript exports resolve those names. The live cue request still uses its fixed Speaker label. A separately generated meeting-notes request includes remote labels and custom names in its prepared body and fingerprint, so renaming invalidates an earlier review. Diarization is not identity verification. After a reconnect, the feed drops speaker IDs for the rest of that session so reused provider IDs cannot inherit an old custom name. Live rename commands also carry the main snapshot session token and reject a replacement session.

### Meeting-notes validation recovery

`meeting_notes.rs` rejects the entire reply when an item fails citation, owner, date, text or section bounds. A validation failure alone can enable one explicitly reviewed retry, with at most two sent attempts. Rust reserves each sent attempt's full worst-case estimate, including responses with missing usage, and refuses a combined estimate over $1. Unknown pricing on either attempt blocks retry. Unsent key/offline/cancel paths restore the previous failure without consuming an attempt. No automatic resend, model fallback, partial repair or validator relaxation occurs. Existing notes plan/write commands accept an optional retry flag; the retry confirmation digest binds the exact request, session and attempt generation. Worker callbacks also carry the generation, so late abandon/finish callbacks cannot release or replace a newer attempt. A new session clears the memory-only record.
