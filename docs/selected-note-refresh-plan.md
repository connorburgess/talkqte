# Selected-note refresh: proposed boundary

Status: planning, 13 November 2026, with [one explicit check](#first-slice-one-explicit-check-simulated-provider-only) built against a simulated provider only. This proposes a refresh option for the optional TalkQTE notebook; it does not implement polling, background operation, new retention or a live transcript. The user task is to keep a small, explicitly selected set of prior notes current without losing control of which notes the app reads or mistaking old context for the current meeting. The [roadmap](../ROADMAP.md#future-goal-work-with-other-note-taking-apps) keeps this work open.

## Starting point and provider limits

Today the user can manually reimport selected Granola notes. The observed `updated_at` mapping replaces a copy only with a newer revision; missing or invalid revisions do not establish ordering. Fictional server checks exercise that contract, and the owner confirmed a basic native import and removal. Automatic refresh, real-account update visibility, refresh ordering and recovery have not been verified. See [import evidence](granola-import-validation.md#refreshing-an-imported-note).

The [Granola MCP guide](https://docs.granola.ai/help-center/sharing/integrations/mcp), checked 13 November 2026, describes `get_meetings` for accessible notes, individual-user OAuth and active-workspace scope. It limits Basic access to notes from the last 30 days and describes rate limits that vary by plan and tool, with a changeable average across tools. These descriptions do not establish a notification stream, a guaranteed update delay, stable deletion signals or a safe polling interval. Verify the exact contract and the person's entitlement before implementation. MCP transcript access and provider writeback are different capabilities; neither is part of this proposal.

## Proposed session contract

- **Explicit selection and start:** refresh is off by default. A person chooses which already imported Granola copies may refresh and explicitly starts it for the current app session. Show the provider, selection count and what leaves the device before starting. A new note, another provider, another workspace, reconnect or restart cannot silently enlarge or restart that selection.
- **Bounded work:** permit at most one refresh request at a time, with a bounded selected set and no overlapping background queue. A timeout does not prove that the sent request ended: do not start a replacement until it has settled or a separately verified mechanism guarantees the same bound. Choose a conservative interval, timeout and bounded backoff only after measuring provider behavior and accounting for other tools sharing the account's limits. A rate-limit response stops immediate retries and is visible; do not interpret the published average as an allowance for TalkQTE alone.
- **Identity and ordering:** bind every request and response to the connection generation, active workspace, session and selected note identity. An externally changed workspace may not change local state; verify a provider-supported binding across the request and fail closed if that cannot be established. Accept a result only if all identities are still current. Compare a trustworthy provider revision before replacing a copy; an older, equal or unversioned response must not overwrite a known newer copy. A missing revision is not evidence that content is fresh. Existing manual-import behavior remains separate until an implementation explicitly changes it.
- **Removal, Stop and Disconnect:** removing a note immediately removes it from the refresh selection and invalidates any in-flight result for it. Stop prevents future requests and discards pending results; Disconnect also retires the connection, while existing local copies remain until separately removed. An HTTP request already sent may finish at the provider; the app must not claim it was recalled. Restarting refresh or reconnecting requires an explicit user action and a current selection.
- **Uncertain availability:** an omitted note, scope change, 30-day limit, malformed response or failed request does not by itself prove deletion. Mark the affected copy as not verified and explain the next action; do not silently replace, delete or re-add it. Before an implementation enables refreshed copies as cue sources, define and test whether an unverified copy is excluded from new cues and how a displayed or held cue is invalidated. Do not present stale context as current.
- **Freshness and privacy:** distinguish last successful check from the provider's last-update time; neither proves when a person last edited the source. Report per-note freshness and errors without logging note content, identifiers or tokens. Keep copies and selection in memory only; do not upload, write back or persist them as a side effect of refresh.

The initial presentation should keep Stop refresh and Disconnect available during a wait, show a recoverable offline/expired/rate-limited state, and avoid a misleading green "current" label while any selected note is unresolved. A quiet local demo and cue controls must remain usable while the provider is unavailable. These are proposed requirements, not implemented behavior or accessibility evidence.

## Acceptance before enabling refresh

Use a fictional provider first, with a named clock and deterministic delayed responses. At minimum check:

1. Only explicitly selected IDs are requested; enabling, adding, removing and reconnecting never widen the selection. Session replacement and Stop discard late success and late error responses.
2. Newer revisions replace the same selected copy, while equal, older, missing, invalid and out-of-order revisions cannot roll back a known newer copy. Per-note last-check and provider-update times remain distinguishable.
3. Removal, Disconnect, an externally initiated workspace switch and reconnect during a delayed request cannot restore a removed note or apply a retired response. An unverifiable workspace binding fails closed. The UI preserves separately retained copies on Disconnect and offers explicit removal.
4. Partial, missing, malformed, offline, expired/revoked and rate-limited results remain visible as distinct recoverable states. No error is described as deletion without provider evidence. The selection, retained copies and eligibility of each source for a new or held cue follow the approved policy.
5. At most one bounded request is outstanding, including after a local timeout; timeout, backoff, cancellation and explicit retry are measured under slow and unavailable providers. No new request starts after Stop, and no meeting content or credentials appear in logs or diagnostics.
6. Keyboard and screen-reader routes expose selection, freshness, Stop, Disconnect and recovery in narrow windows. A synthetic long-session check measures request rate and device cost. These checks are not a real-account or user-outcome result.

Then conduct a separately authorized account check with a selected note: source/date and update visibility, changed and missing revisions, access loss or workspace change, Stop and reconnect. Record only bounded observations without retaining meeting content. Review provider terms and current limits again before enabling refresh; verify that any network request and scope are clear to the person. The next release blocker remains dependable, permission-scoped behavior and recovery on a real account, not the absence of a polling timer.

## First slice: one explicit check, simulated provider only

13 November 2026. The smallest useful part of the contract is built: a person presses **Check for updates** and TalkQTE asks once about the Granola notes already selected. There is no timer, schedule, retry or background queue, and nothing new is stored. **The signed-in Granola connection does not offer this control.** The check requires the provider's own identifier for the active workspace, and the tools this client has observed name none, so `granola.rs` reports the binding as unsupported and the command refuses; the check itself also stops before any note identifier is sent. Everything below is exercised with fictional providers: a scripted source in Rust and a simulated native boundary in the browser tests.

What the slice does, in `src-tauri/src/context_refresh.rs`:

- **Selection:** only Granola copies kept when the check starts are requested, ten identifiers per request, one request after another. Notes the provider adds to a reply are dropped; a file note with the same identifier is untouched. The store can replace a kept copy but never add one.
- **Workspace:** the identity is read before the first request and after each one. A missing identity, a change during the check, or a workspace other than the one this connection's first successful check saw applies nothing. A switch between importing a note and the first check is not detected, because imports record no workspace.
- **One request:** a second check cannot start while one runs. After the 20-second local wait ends, or after Stop or Disconnect, the sent request still counts until it actually finishes; a new check is refused until then, and the ended check sends no further batch.
- **Results:** a newer provider update time replaces the copy through the existing store rule, which also retires a reminder quoting the old revision. The same time confirms the copy. An omitted note, an older reply, a reply without an update time or without a readable date or text keeps the copy and marks it not verified; none is described as deleted. Offline or unusable replies, expired sign-in, withdrawn access, a requested pause and an unreadable format are separate visible states, and none is retried automatically.
- **Stop, Disconnect, removal:** each invalidates the pending result. Disconnect also forgets earlier findings. A removed note leaves the selection at once: it is not asked about in a batch that has not been sent yet, and a reply already on its way cannot touch it, including when the note is imported again before that reply arrives. A check stopped before its first request sends nothing, not even the workspace read. Leaving the notebook stops a pending check.
- **Freshness:** each checked note shows when a check last confirmed or updated it by this device's clock, separately from Granola's update time for the kept copy. Results are words, not a color, and live in memory until disconnect, removal, a later import of another revision, or restart.

Not covered by this slice: an interval or any automatic refresh, choosing a subset of the kept notes, a policy for excluding an unverified copy from new or held reminders (unverified copies stay eligible exactly as before a check), measured timeout and rate-limit values, and request-rate or device-cost measurement. Acceptance items 1 to 5 above are met only in part and only for a single explicit check; item 6 has keyboard-activation and narrow-window browser checks, not screen-reader evidence. Evidence and limits are in the [validation record](granola-import-validation.md#explicit-update-check-against-a-simulated-provider).

Next blocker: a provider-supported workspace identity. Acceptance check: in a separately authorized account session, establish whether Granola exposes one through a documented tool or field, record only its shape, and only then decide whether the real connection may offer the check.
