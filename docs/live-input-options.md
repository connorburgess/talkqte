# Live meeting text from tools people already use

Can TalkQTE get the words of a meeting while it is happening from a note-taker or meeting platform the person already uses, instead of, or as well as, capturing audio itself? This record answers that for roadmap item **N3** and for how much of native capture (**T2**) is on the critical path. It is a documentation check, not an integration.

Checked **14 November 2026** against official developer documentation, help centers, pricing pages and terms. Nothing was signed up for, no account or API key was used, no API was called and no company was contacted, so nothing here is observed behavior. A linked statement is documented by that page. **Claimed** marks marketing copy or a third party. **Not answered** means the linked pages were read and did not say. Provider interfaces, plans and terms change; recheck them before building anything. Reading a term here is not a legal conclusion.

## Answer

**No documented source removes TalkQTE's own capture from the critical path.** T2 stays on it.

- **Granola**, the first-priority note-taker, documents no live interface: its API returns only notes that already have an AI summary, which it writes after the call. **Fathom** and **tl;dv** say their transcripts come only after the meeting. **Otter** offers its API on Enterprise only, and its readable pages document no live feed.
- **Google Meet**, the first target meeting app in the [budgets](budgets.md), documents no supported live text for another app. Its Media API carried audio and video only, is discontinued, and shuts down on 15 January 2027.
- **Zoom**, the second target, offers live transcripts through Realtime Media Streams (RTMS), on a paid plan with a Developer Pack, with a disclosure to everyone in the meeting. Basic (free) accounts are not supported, and the stream is signed with an app secret that a distributed desktop app cannot hold, so it needs a server TalkQTE would run.
- Two note-takers document live text that a desktop app could fetch itself with the person's own account: **Fireflies** (Realtime API, beta) and **Read AI** (live meeting endpoint, open beta). Both work only when that note-taker is already capturing the meeting in its cloud. The facts that decide usefulness (bot-free capture, whether a segment is final, delay) are not documented, and both sets of terms need the provider's reading before anyone distributes a client.
- **Microsoft Teams** documents real-time transcripts for apps through Work IQ. From 14 November 2026 an organization setting, off by default, gates them; use is billed, and the reviewed pages document no delivery interface. **Webex** delivers live captions only to its browser SDK joining as a participant, on paid licenses.

So provider live text could at most be an optional second source for people who already let Fireflies or Read AI capture their meetings. It cannot replace local capture of both sides of a call, which the [first technical milestone](../ROADMAP.md#first-technical-milestone) requires anyway, and it does nothing for people whose record lives in Granola.

## What counts as live input

Live input means words that reach TalkQTE while the conversation is still going, soon enough for a cue: the agreed target is a median of 3.5 seconds and a 95th percentile of 5 seconds from speech to transcript line ([budgets](budgets.md)). A transcript available only after the meeting is prior-note import (N2, N4, N5), and sending results back is writeback (N6); this record mentions those only for contrast.

The engine's one transcript input, `Engine::ingest`, accepts only final segments in time order with a unique ID, on the session clock ([architecture](architecture.md#current-prototype)). Every live provider feed below either revises segments after sending them or does not say whether it does, so any adapter would first need a step that turns revisable provider text into final, ordered segments.

## Note-takers

### Fireflies

This is the check N3 asks for. The realtime pages carry modification dates of October and November 2025; the plan, terms and help pages were current in September to November 2026.

- **Live text, in beta.** The [Realtime API overview](https://docs.fireflies.ai/realtime-api/overview) lets an application "receive **live transcription events** over WebSockets" and says "The Realtime API is currently in **beta**. Features and endpoints may change." No deprecation is announced.
- **Connection.** In [getting started](https://docs.fireflies.ai/realtime-api/getting-started), a Socket.IO client connects to `wss://api.fireflies.ai` with path `/ws/realtime`, passing the API token and a `transcriptId` in its handshake. On failure "the server emits an `auth.failed` event and disconnects the socket." The app opens the connection, so no inbound server is needed. A Rust client would need a Socket.IO implementation, not a bare WebSocket.
- **Finding the meeting.** The same page points to the [`active_meetings` query](https://docs.fireflies.ai/graphql-api/query/active-meetings); "Regular users: Can only query their own active meetings". Webhooks would need a public HTTPS host ([Webhooks V2](https://docs.fireflies.ai/graphql-api/webhooks-v2)), so polling is the desktop route.
- **The bot.** The `active_meetings` query's [meeting state](https://docs.fireflies.ai/schema/enum/meeting-state) `active` is described as "The meeting is currently in progress with the Fireflies bot actively recording." The bot "appears in the participant list and posts a message in the meeting chat" and cannot be hidden ([joining FAQ](https://guide.fireflies.ai/articles/9554534786-how-fireflies-joins-and-records-your-meetings-faqs)). Fireflies' desktop app can also record from system audio, and then "No Fireflies.ai Notetaker joins the call"; in that mode Fireflies' own app still shows a "Real-time transcript" and Live Assist "notes and suggestions during the meeting" ([bot-free recording](https://guide.fireflies.ai/articles/6666374717-how-to-record-meetings-without-a-bot-on-the-fireflies-desktop-app)). **Not answered:** whether bot-free sessions appear in `active_meetings` or produce realtime events for other apps.
- **Events and revisions.** The [event schema](https://docs.fireflies.ai/realtime-api/event-schema) sends `transcription.broadcast` "for every new transcription segment or update", with `transcript_id`, `chunk_id`, `text`, `speaker_name`, and `start_time` and `end_time` in seconds. "If the transcription is being updated, it will contain the same chunk_id as the previous event. A new transcription will have a different chunk_id". **Not answered:** a final flag, delivery order, whether an earlier chunk can still change after a newer one starts, where `start_time` is measured from, reconnect or replay of missed events, and an end-of-meeting event. The overview claims "Data is streamed as soon as it's transcribed" and gives no figure.
- **Polling alternatives.** On a [transcript](https://docs.fireflies.ai/schema/transcript), "When `is_live` is `true`, the `sentences` field returns real-time captions from the ongoing meeting." Fireflies' MCP server at `https://api.fireflies.ai/mcp`, over Streamable HTTP, "uses OAuth with your Fireflies account" ([MCP setup](https://docs.fireflies.ai/getting-started/mcp-configuration)); its transcript tool "returns a point-in-time snapshot of the live transcript with sentences captured so far", and it has an active-meetings tool ([MCP tools](https://docs.fireflies.ai/mcp-tools/overview)). That route uses the same transport as TalkQTE's Granola connection and avoids holding an API key. **Not answered:** whether its OAuth uses dynamic client registration, as Granola's does, and whether it accepts a desktop loopback redirect. The limits page applies its quota errors to MCP tool calls too. Polling every 10 seconds would use a Free plan's 500 daily requests in about 83 minutes, or about 14 hours during the first 14 days at Pro limits (arithmetic, not documented figures).
- **Account and plan.** The key is the person's own ([authorization](https://docs.fireflies.ai/fundamentals/authorization)). The Realtime overview claims "Secure connections with scoped access" but no page defines a scope, so this record assumes a key can reach everything the account can. "Every Fireflies plan, including Free, can use the API" ([API page](https://fireflies.ai/api)). The [limits](https://docs.fireflies.ai/fundamentals/limits) are 30 requests a minute and 500 a day on Free and 60 and 5,000 on Pro, and "a Free user's first API request starts a 14-day trial at Pro limits". **Not answered:** whether Realtime needs a particular plan or beta enrollment, connection limits, and whether socket use counts against the request quota.
- **Key handling.** The authorization page says "Never expose it in client-side code", and the API page says "use it only from your own servers, and never put it in a web page or mobile app." Desktop apps are not mentioned.
- **Consent and notice.** The bot's chat message "alone may not meet consent laws, so tell participants and get consent where required" (joining FAQ). Bot-free recording has a watermark, a spoken notice and a chat message by default, and "If you disable a consent or notification option, you are responsible for informing participants" (bot-free recording). The [terms](https://fireflies.ai/terms-of-service) require that "each meeting participant consents to recordings".
- **Retention and region.** Account data is kept "for as long as your account remains active" ([privacy policy](https://fireflies.ai/privacy-policy), last updated 28 September 2026); per-meeting auto-delete is "exclusive to Fireflies Enterprise users" ([auto-delete](https://guide.fireflies.ai/articles/7870593373-learn-about-the-auto-delete-meeting-feature)). Data is "stored and processed in Fireflies' secure cloud infrastructure in the United States" by default ([data storage](https://guide.fireflies.ai/articles/9596505232-learn-about-data-storage-and-transfer)). **Not answered:** regional realtime endpoints.
- **Terms.** The [terms of service](https://fireflies.ai/terms-of-service), last updated 28 September 2026, let users "access and use the APIs for the sole purpose of accessing the Services as permitted by these Terms and in accordance with any documentation we provide" (11(b)). They also prohibit "Develop or use any applications or software that interact with our Services without our prior written consent" and incorporating the service on a "stand-alone basis" (6(a)). For a third-party client those clauses pull in different directions; no separate API terms were found.

### Read AI

Read AI was not on the starting list. Its human help pages refused automated requests, so they were read through the help-center feed that [Read AI's llms.txt](https://www.read.ai/llms.txt) names as the "Canonical machine-readable source"; the text is official but was not seen rendered.

- **Live text, open beta.** The [API reference](https://support.read.ai/hc/en-us/articles/49381161088659-API-Reference), edited 29 October 2026, offers `GET /v1/meetings/{id}/live` to "fetch real-time transcript and chapter summaries as the meeting progresses, with optional filtering by start time". The REST API "is currently available as an open beta release." A meeting in progress has no `end_time_ms`, and the meeting list "returns both active and ended meetings".
- **Live only when switched on.** "Live meeting data, including the live transcript, is available through the API and MCP server, but by default it's only available for a meeting if someone has the live meeting dashboard open during the meeting", unless the person enables "Live Transcription" in account settings ([API and MCP overview](https://support.read.ai/hc/en-us/articles/49379985941523-Read-AI-API-and-MCP-Overview)). Members of a workspace also need its Downloads option enabled.
- **Connection.** Polling over HTTPS, with no server. "The Read AI API uses OAuth 2.1 with dynamic client registration", it "doesn't issue static or long-lived API keys", access tokens last 10 minutes, and refresh tokens last about six months and "are rotated on every use" ([authentication](https://support.read.ai/hc/en-us/articles/49380809380371-API-Keys-Authentication)). That is the same sign-in style as TalkQTE's Granola connection. The documented example registers `https://api.read.ai/oauth/ui` as its redirect. **Not answered:** whether a loopback redirect, as the Granola sign-in uses, is accepted.
- **Plan.** "The MCP server and API are available on all plans, including the Free plan", with "up to 100 requests per minute per user" (overview). [Pricing](https://www.read.ai/plans-pricing) lists 5 meeting transcripts a month on Free. **Not answered:** whether live use counts against that.
- **Revisions and latency.** Each turn carries a speaker, text, and start and end times in milliseconds. **Not answered:** whether a returned turn can change, ordering guarantees, and delay.
- **Presence and consent.** In web mode Read "Appears in the participant list under its own name, or appears as a persistent icon" and may post a chat message; "In desktop and mobile mode, the user running Read AI is responsible for telling other participants and collecting consent" ([consent modes](https://support.read.ai/hc/en-us/articles/52118970003987)). **Not answered:** whether desktop-mode meetings produce live data.
- **Retention and region.** On Free, "report text is kept for no longer than 2 years, and recordings are deleted 180 days after the meeting" ([retention](https://support.read.ai/hc/en-us/articles/25702259763091)); storage defaults to AWS us-east-1, and EU and Canadian deployments are offered ([regions announcement](https://www.read.ai/post/read-ai-brings-international-data-processing-and-storage-to-global-customers)). **Not answered:** an EU base address for the REST API.
- **Terms.** The [terms](https://www.read.ai/termsofservice), last updated 26 February 2026, prohibit "Sell, resell, or commercially use our Services" and scraping; no API-specific terms were found. **Not answered:** how this applies to an open-source client that each person runs with their own account.

### Otter, Fathom and tl;dv

- **Otter.** The [pricing page](https://otter.ai/pricing) (last updated 27 October 2026) lists "Otter API and webhooks" on Enterprise only. The Public API (beta) article listed in [Otter's llms.txt](https://otter.ai/llms.txt) refused automated requests, and so did its MCP Server article; whether any live endpoint exists is **not answered**. The live transcript link Otter posts in meeting chat is for people, and no page permits reading it programmatically. Otter also announces Live Assist, "real-time, private coaching" shown "as a small, unobtrusive prompt within the virtual meeting" ([announcement](https://otter.ai/blog/otter-rethinks-the-meeting-new-ai-preps-you-coaches-you-and-follows-through), claimed): a related product, not an interface TalkQTE could use.
- **Fathom.** The [developer FAQ](https://developers.fathom.ai/faq) asks "Is real-time or live transcript available via the API?" and answers "No. Transcripts are available only after post-call processing completes."
- **tl;dv.** The [API reference](https://doc.tldv.io/) says "The transcript is returned only if it is complete", and the [API is on Pro or Business plans](https://intercom.help/tldv/en/articles/11583137-api).

These remain possible sources of completed notes (N4), not live input.

### Granola

- **Nothing live.** The [API introduction](https://docs.granola.ai/introduction) says "The API only returns notes that have a **generated AI summary**", and Granola generates those notes "Once Granola has recognised your call has ended, or you stop it manually" ([enhanced notes](https://docs.granola.ai/help-center/taking-notes/ai-enhanced-notes)). [Webhooks](https://docs.granola.ai/webhooks) cover `note.generated`, `note.edited` and `note.access_granted` and must go to a URL that is "HTTPS and publicly reachable". The [MCP guide](https://docs.granola.ai/help-center/sharing/integrations/mcp) does not say whether a meeting in progress is listed, and its transcript tools are paid-only. No local desktop interface is documented, and TalkQTE does not read Granola's private storage.
- **Consequence.** Granola stays a prior-note source. For people whose record lives in Granola, the live words can only come from TalkQTE's own capture.
- **Terms.** Granola's [Platform Terms](https://www.granola.ai/static/Granola-Platform-Terms-2025-12-19.pdf), last updated 19 December 2025, bar using the services "for purposes of building an application, service, or product that is competitive with any Granola product or service or has similar ideas, features, functions" (3.4(vi)). That clause concerns the existing prior-note connection as much as any live one; how Granola reads it for a companion that uses a person's own notes is **not answered**.

### Developer services such as Recall.ai

[Recall.ai](https://docs.recall.ai/docs/bot-overview) documents real-time transcripts from meeting bots and from a bot-free Desktop Recording SDK. It is infrastructure for developers, not a tool people already use: TalkQTE would hold its own account, pay "$0.50/hr of recording" plus transcription ([pricing](https://www.recall.ai/pricing)), run a backend, and ship an npm package ("Bindings for other languages aren't currently available", [SDK FAQ](https://docs.recall.ai/docs/desktop-recording-sdk-faq)). Meeting audio would go to a new processor. For the desktop SDK, "There is no recording indication, the responsibility is on your user to notify others" ([product page](https://www.recall.ai/product/desktop-recording-sdk)). [Attendee](https://attendee.dev/changelog) documents a similar beta. Neither fits [PRIVACY.md](../PRIVACY.md) or the project's [operating estimates](operating-estimates.md), which assume no project-paid processing.

MeetGeek, tactiq, Notta, Krisp, Avoma, Sembly, Supernormal, Jamie, Bluedot, Circleback and Fellow were also searched, some only through search results; none documents a live transcript feed for other apps on the pages found.

## Meeting platforms

### Zoom

- **Realtime Media Streams.** [RTMS](https://developers.zoom.us/docs/rtms/) is "a data pipeline that gives your app access to live audio, video, and transcript data from Zoom meetings", [generally available since 25 June 2025](https://developers.zoom.us/changelog/rtms/june-25-2025/). "Zoom sends `meeting.rtms_started` … webhook events when RTMS streaming starts" ([working with streams](https://developers.zoom.us/docs/rtms/meetings/work-with-streams/)), and webhook endpoints must be "a publicly accessible `https` endpoint" ([webhooks](https://developers.zoom.us/docs/api/webhooks/)). Zoom also offers [WebSocket event subscriptions](https://developers.zoom.us/docs/api/websockets/), which need no public endpoint, but they use the app's "client ID and secret" and are "'bound' to the account that creates them, and are not intended for multi-tenancy"; whether RTMS events are offered there is **not answered**. Either way the stream handshakes are signed with the app's client secret, which a distributed desktop app cannot hold, so this needs a TalkQTE-run server receiving meeting content.
- **Plan.** "Basic (Free) | Not supported | RTMS webhooks will not fire"; paid plans need a Zoom Developer Pack ([troubleshooting](https://developers.zoom.us/docs/rtms/troubleshooting/)). Per-minute prices were not shown on the pages read.
- **Notice and approval.** Everyone sees "The content of this meeting is being sent to one or more apps." and the app's name in the participant's video tile ([host experience](https://developers.zoom.us/docs/rtms/meetings/ux-host/)); the host sees a request to "Allow or Deny" only "if you require approval to share content", and not "for an app that's already been given permission to start in the web settings"; an account admin can set apps to auto-start (same page). No bot joins.
- **Text.** "Transcripts arrive continuously as speech is detected and processed in real time", optimized "for low latency" ([media](https://developers.zoom.us/docs/rtms/meetings/media/)). **Not answered:** latency in seconds and whether a segment is revised.
- **Meeting SDK.** A [Meeting SDK](https://developers.zoom.us/docs/meeting-sdk/macos/default-ui/advanced-features/raw-data/) client is a participant that can receive raw audio and Zoom's live transcription messages, which are added, updated and completed in place ([macOS SDK reference](https://marketplacefront.zoom.us/sdk/meeting/macos/_zoom_s_d_k_errors_8h.html)). Zoom's [changelog](https://developers.zoom.us/changelog/meeting-sdk/requiring-authorization-for-meetings-joined-outside-of-an-apps-account/) announced that from 23 February 2026 such apps "will need to attribute to a user when joining meetings outside their own Zoom account", and "All apps must go through app review in order to access meetings or webinars hosted outside the developer account" ([On Behalf Of tokens](https://developers.zoom.us/docs/meeting-sdk/auth/obf/)). Raw recording triggers "the recording consent dialog for all users". It would be a second Zoom client beside the person's own; out of scope.
- **No other read path.** The Zoom Apps SDK has no transcript or caption method and points to RTMS ([data access](https://developers.zoom.us/docs/zoom-apps/data-access/)); the [caption API token](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0060368) sends captions into Zoom, not out. Cloud-recording transcripts arrive "after the recorded meeting/webinar ends" ([events](https://developers.zoom.us/docs/api/meetings/events/)).
- **Terms.** The [API License and Terms of Use](https://www.zoom.com/en/trust/legal/zoom-api-license-and-tou/), last updated 16 July 2025, permit use by others only if the app "has been published to the Zoom App Marketplace" or Zoom approves in writing (6.1). They prohibit using API data to train AI models, and "To scrape, build databases, or otherwise create copies of any data accessed or obtained using the Zoom APIs". They also make the developer responsible that "all consents have been obtained from, and all notices … have been given to, all End Users".

### Google Meet

- **Media API, discontinued.** "The Google Meet Media API Developer Preview Program is discontinued and will not proceed to General Availability (GA). New signups are now closed. Existing participants will retain access until endpoints shut down on January 15, 2027." ([Meet developer home](https://developers.google.com/workspace/meet), last updated 28 October 2026). Its guide pages now return not found; the [archived overview](https://web.archive.org/web/20260930135317/https://developers.google.com/workspace/meet/media-api/guides/overview) shows it carried video, audio and participant metadata, not text, and required every participant to be enrolled in the preview. This confirms the record in the [mobile plan](mobile.md#current-feasibility-limits).
- **REST API.** The [REST API overview](https://developers.google.com/workspace/meet/api/guides/overview) lists "access granular transcript speech entries" under "After a conference"; "During a conference" covers metadata, participants and lifecycle events. "Transcript entries provided by the Meet REST API are deleted 30 days after the conference ends" ([artifacts](https://developers.google.com/workspace/meet/api/guides/artifacts)). **Not answered:** whether entries can be listed while transcription is still running.
- **Add-ons and captions.** The [add-ons SDK client](https://developers.google.com/workspace/meet/add-ons/reference/websdk/addon_sdk.meetaddonclient) has no transcript, caption or audio method. Captions are per viewer: "The captions are turned on only for you" ([Meet help](https://support.google.com/meet/answer/15077804)). No supported way for another app to read captions was found; extensions that read the page are not an interface.
- **Policy.** The [Workspace API user data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) restricts use of Meet data and prohibits using it "to create, train, or improve a machine learning or artificial intelligence model beyond that specific user's personalized model".

### Microsoft Teams

- **Work IQ real-time transcripts.** "Work IQ lets agents and apps, including ones your organization builds, receive the transcript of a Teams meeting or call while it's in progress." The setting is "off by default" and "takes effect on November 14, 2026" ([admin page](https://learn.microsoft.com/en-us/microsoftteams/meeting-transcript-api-access), last updated 26 October 2026). The page adds: "If apps in your organization already receive real-time transcripts through Work IQ, turn on Work IQ access before that date to keep them working." An app receives it only when AI is allowed in the meeting, "Transcription is running. Work IQ doesn't start transcription.", and the app "acts on behalf of a signed-in user"; "The organizer's organization decides." Work IQ uses delegated sign-in only, its [permissions](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/work-iq/permissions) are marked "AdminConsentRequired - Yes", and it is paid "through a usage-based model that uses Copilot Credits" ([API overview](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/work-iq/api-overview)). Its [product terms](https://www.microsoft.com/licensing/terms/productoffering/MicrosoftIQ/MCA) forbid using it "to redistribute, resell, or sublicense any data obtained using the APIs." **Not answered** by the Work IQ developer pages read: the endpoint, protocol, scope, latency and revision model for transcripts. This is a work-tenant feature an organization must enable and pay for, not something an individual can turn on.
- **Media bots.** Application-hosted bots get raw media, are "in developer preview", must run on "Windows Server … in Azure" and be "developed using C#" ([requirements](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/calls-and-meetings/requirements-considerations-application-hosted-media-bots)); Microsoft says "Real-time Media bots are not recommended for AI agent scenarios" ([concepts](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/calls-and-meetings/real-time-media-concepts)). Persisting media or derived data requires calling `updateRecordingStatus` first ([recording status](https://learn.microsoft.com/en-us/graph/api/call-updaterecordingstatus)). Out of scope.
- **After the meeting.** Graph transcripts are fetched "after the meeting or call ends" ([transcripts overview](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/meeting-transcripts/overview-transcripts)). Meeting apps can send captions into a meeting but have no documented way to read them ([meeting app APIs](https://learn.microsoft.com/en-us/microsoftteams/platform/apps-in-teams-meetings/meeting-apps-apis)).

### Webex

- **Browser SDK captions.** The [Meetings SDK guide](https://developer.webex.com/meeting/docs/webex-meetings-sdk-web-advanced-meeting-controls) starts transcription with `startTranscription()` and delivers text on `meeting:caption-received`, with an `isFinal` flag. "Real-Time Transcription is ONLY supported by meetings where Webex Assistant can be enabled, which requires a paid license." ([browser SDK](https://developer.webex.com/docs/sdks/browser)). The SDK is a meeting client running in a browser; whether it runs in Tauri's webview is **not answered**.
- **After the meeting.** REST transcripts: "Transcript will be saved after meeting ends only if related settings and organizational policies allow." ([transcripts API](https://developer.webex.com/meeting/docs/api/v1/meeting-transcripts)).
- **Announced.** Media Intelligence RTMS would deliver audio and video "without requiring a bot" and "is planned for limited availability by end of the year and for purchase in early 2027" ([Webex blog](https://blog.webex.com/collaboration/announcing-media-intelligence/), 16 October 2026; claimed until released).
- **Consent and terms.** "Before a meeting can be recorded, summarized, or transcribed, everyone participating needs to give their consent" ([AI Assistant help](https://help.webex.com/en-us/article/nyzkuik)). The [developer terms](https://developer.webex.com/terms-of-service) forbid copying Webex data "except as necessary to enable the intended feature of your App and with express consent" of end users.

## Recommendation

**No adapter code yet.** Keep T2 as the critical path. For N3, the next bounded step is the owner's Fireflies check below: one short session on the owner's account, plus a written question to Fireflies, covers the four things the documentation leaves open (bot-free capture, finality and delay, plan access, and the terms question). The session gives observations on one account and one meeting, not guarantees. Fireflies stays the candidate because the product names it second after Granola. Read AI is technically as close, with a sign-in that matches the Granola connection more closely, and the same check applies if the owner or likely users prefer it.

Stop N3's live-input work, and record why, if any of these hold:

- Realtime events come only while Fireflies' bot is in the meeting, and the owner does not want a bot in meetings TalkQTE accompanies.
- A Free or Pro key cannot connect, or Realtime needs enrollment that is not offered.
- Over a fictional meeting, the delay from a spoken line to its last update exceeds the 5-second 95th-percentile budget.
- Fireflies answers in writing that an open-source desktop client using a person's own key needs consent it will not give.

Only if none hold, the next bounded step is the [fixture contract](#if-the-check-passes-a-fixture-contract), still with no network code.

## What a free-tier check needs from the owner

This is for the owner to run or explicitly authorize; no lane may sign up, sign in or hold a key.

- **An account and a plan choice.** The owner's own Fireflies account; Free is enough to learn whether Realtime accepts a Free key. Free includes "3 free meeting transcriptions" by default ([free plan](https://guide.fireflies.ai/articles/6176608577-learn-about-fireflies-free-plan-features)), and the first API request starts a 14-day trial at Pro limits, so the check measures Pro limits.
- **A fictional meeting.** Two devices or two people reading a fictional script, such as the bundled demo, in Google Meet (the first target app), recorded twice: once with the Fireflies bot invited and once with bot-free desktop recording. No real meeting, names or content.
- **A key kept out of everything.** Created by the owner, given to a small throwaway listener outside the app through an environment variable or standard input, never on a command line, in a log, in the repository or in the app. Revoke it and delete the fictional meetings in Fireflies afterwards.
- **Both routes.** The Realtime socket with the key, and the MCP live snapshot with an OAuth sign-in, so their delay and limits can be compared.
- **What to record** for each run, without account identifiers: whether `auth.success` arrives; whether and when the meeting appears in `active_meetings`; the exact event shape; how many updates each `chunk_id` receives and whether an older chunk changes after a newer one starts; the delay from a spoken marker line to its first and last update; what happens after a short network drop and at meeting end; whether `/ff pause` stops events; and the rate-limit headers on the next GraphQL request.
- **The terms question.** The owner, not a lane, asks Fireflies in writing whether 6(a)'s "prior written consent" and the "only from your own servers" advice apply to an open-source desktop client that each person runs with their own key, and records the answer before any distribution.

Not checkable on a free tier: Zoom RTMS (Basic accounts are not supported), Teams Work IQ (needs an organization's administrators and billing) and Webex captions (paid licenses). Google Meet has nothing live to check. One optional, cheap Granola check: while a fictional Granola note is recording, open the existing Granola chooser in the development build and see whether the meeting is listed; transcripts there stay paid-only.

## If the check passes: a fixture contract

The step after a passing check is a Rust contract, tested only with fictional fixtures, that turns a provider's revisable segments into the final, ordered segments `Engine::ingest` accepts. Its shape follows the documented Fireflies event; the rules are TalkQTE's own:

- A segment stays provisional until a newer `chunk_id` arrives, a bounded quiet period passes, or the meeting ends; only then is it ingested. Cues never come from provisional text.
- A later update to an already ingested segment is counted and dropped, not shown as a correction, until the engine can revise a line.
- Duplicates, events for another meeting, and segments that would move backwards in time are refused and counted.
- Provider seconds are mapped to the session clock from an explicit anchor recorded when the first event arrives, and text and speaker labels are bounded to the engine's limits. A provider's speaker name is external content, not addressee detection.
- Failed sign-in, revoked keys, rate limits and dropped connections use the existing connection statuses in `src-tauri/src/context.rs`; a dropped connection leaves a visible gap and never reconnects silently. Stop and Disconnect discard provisional text.

Acceptance: fictional fixtures for an updated segment, a late revision, a duplicate, a gap, a reconnect and a meeting end all reach the engine without rejection, and none raises a cue before its segment is final. Network code, sign-in and key storage stay out of that step.
